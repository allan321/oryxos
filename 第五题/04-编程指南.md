# 编程指南：OryxOS 的 AI 辅助开发策略

> **本文定位**：回答"AI 怎么帮我们写出代码"——工具选型、工作流设计、两阶段策略。
> **前置文档**：[业界调研](./01-业界调研.md) → [需求分析](./02-需求分析.md) → [技术方案](./03-技术方案.md)
> **核心结论**：主体开发用 Spec-Kit（结构化规划），增量开发用手动提示词 + Claude Code（灵活高效）。

---

## 一、三种 AI 编程模式的对比

OryxOS 有 9 个 Maven 模块、5 个核心能力、10 个关键技术决策。选对 AI 编程工具直接影响 12 小时的利用效率。以下是三种主流模式的对比：

| 维度 | Spec-Kit | 手动提示词 | 纯 Vibe Coding |
|------|----------|----------|---------------|
| **怎么工作** | 结构化命令链：constitution → specify → plan → tasks → implement。每个阶段产出文档，下游消费上游 | 在 Claude Code/Cursor 中手写提示词，描述要做什么，AI 直接生成代码 | 不做规划。打开 IDE，脑子里想个大概，让 AI 写代码，跑起来再说 |
| **适用场景** | 从零开始的大型 greenfield 项目；需要多个模块协同；架构决策多、依赖关系复杂 | 修一个 bug、加一个小功能、重构一个类；对已有代码库做增量修改 | 快速原型验证一个想法；个人玩具项目；对代码质量和可维护性无要求 |
| **规划深度** | 深。Constitution 设边界 → Spec 定范围 → Plan 画架构 → Tasks 拆任务。每一层都在上一层约束内 | 中。提示词里可以要求"先想清楚再写代码"，但约束力取决于提示词质量和执行者的纪律 | 浅。没有规划阶段。代码结构在写的过程中"涌现"——或者说，碰运气 |
| **代码质量** | 中高。架构受 Constitution 约束，拆分受 Tasks 约束。但最终代码质量取决于 implement 阶段的 AI 执行 | 中高。取决于提示词质量和 review 纪律。优势是灵活——每个修改的上下文窄，AI 不容易漂移 | 低到中。没有规划 = 代码结构随对话走向而定。前 2 小时很爽，第 3 小时开始重构 |
| **迭代成本** | 较高。每次修改要先改对应文档（spec/plan/tasks），再 implement。小改动也走全套流程 = 浪费 | 低。直接描述改动，AI 出代码。不需要更新规划文档 | 极低（前期）。没有文档负担。但后期重构成本可能吃掉前期省下的所有时间 |
| **团队协作** | 高。Spec/Plan/Tasks 是可共享的文档，多人可并行开发不同 user story | 中。提示词和经验可以写成团队文档，但不如结构化 spec 可传递 | 低。没有文档，代码结构在一个人脑子里，换人维护 = 从零理解 |
| **适合 OryxOS？** | ✅ 主体开发 | ✅ 增量开发 | ❌ |

**结论**：纯 Vibe Coding 不适合 OryxOS——9 个模块、Constitution 8 条硬约束、12 小时时间窗口。没有规划 = 第三周发现架构错了返工。**Spec-Kit 做主体、手动提示词做增量——两个都要，但各管各的阶段。**

## 二、Spec-Kit 对 OryxOS 的匹配度评估

按 5 个维度打分（每维 10 分），基于 OryxOS 001-react-loop-core feature 的实际使用经验：

| 维度 | 评分 | 理由 |
|------|:--:|------|
| **1. 需求对齐度** — Spec 和 Tasks 能多好地反映真实需求？ | **9/10** | Spec 模板强制要求 User Stories + Functional Requirements + Success Criteria 三段式，FR 编号可追溯。Constitution Check 环节确保每条需求对齐 8 条原则。我们在 001 的实践中，从 CLAUDE.md 的"不可违背的原则"直接派生 Constitution，从功能描述直接生成 4 个 User Story + 17 条 FR，需求→spec 的映射零遗漏 |
| **2. 架构约束力** — 能多好地防止实现偏离架构决策？ | **9/10** | Constitution 是硬门禁——plan 阶段逐条 PASS/FAIL。我们在 001 的 plan 中验证了全部 8 条原则，每条有具体 notes 说明如何满足。CLI 命令 enforce 这个检查（不作为可选项），不像手动提示词——AI 可能在第三轮对话"忘记"了架构约束 |
| **3. 任务拆分粒度** — 生成的 Tasks 能直接执行吗？ | **7/10** | 001 生成了 60 个任务，按 4 个 User Story 分 Phase，每个标注文件路径和 [P] 并行标记。够用但有时粒度过细——比如 T036-T038 三个 FileTools 方法分三个 Task，实际可以在一个 Task 内完成。**扣分点**：模板偏 Python/单项目，Java Maven 多模块项目需要手动调整路径约定 |
| **4. 迭代适配性** — 需求变更后重新对齐的成本多高？ | **6/10** | 全套流程（constitution→specify→clarify→plan→tasks→implement→analyze）7 个命令，每个生成/更新文档。改一个需求 → 改 spec → 改 plan → 改 tasks。小改动的流程开销 > 改动本身。**这是 Spec-Kit 最大的弱点**——它假设大部分决策在写代码前做完，不适合"边写边发现"的探索型开发 |
| **5. 学习成本** — 团队要多快能上手？ | **6/10** | 7 个命令、5 个模板、constitution/feature.json/extensions.yml 多个配置文件。init-options.json 中的编号策略（sequential/timestamp）、feature_numbering vs branch_numbering 等概念需要理解。001 实践花了约 30 分钟完成全套 setup。**扣分点**：模板是全英文占位符（`[PRINCIPLE_1_NAME]`），中文项目需要全量替换 |

**总分：37/50**。适合 OryxOS 的**主体开发阶段**（greenfield、多模块、约束多），不适合**增量阶段**（小改动、快迭代）。

## 三、Spec-Kit 的三个关键局限与应对策略

### 局限 1：改一个需求要走全套流程

**症状**：需求分析 v1→v3 期间，加了"不做清单"和"4 周里程碑"两章。如果走 Spec-Kit 全流程，需要重新 clarify → plan → tasks，每个文档都要更新。

**应对**：**只在两个节点走全流程**——(1) 项目启动时（constitution→specify→plan→tasks）；(2) 一个 Feature 完整交付后切换到下一个 Feature 时。中间的小需求变更（如加一条 FR、调整一个技术决策）**手动编辑对应文档**，不重新跑命令。

```
用 Spec-Kit 全流程的节点:
  ★ 项目启动（Feature 001）
  ★ 切换到 Feature 002

不用 Spec-Kit、手动改文档的节点:
  · 加一条 FR
  · 调整一个技术决策
  · 修改一个 Task 的优先级
  · 更新数据模型字段
```

### 局限 2：模板对 Java 多模块项目不友好

**症状**：tasks-template.md 默认路径是 `src/models/`、`tests/contract/`——Python/Node.js 单项目结构。OryxOS 是 `oryxos-core/src/main/java/com/oryxos/core/loop/ReActLoop.java`——路径深度和模块前缀完全不同。

**应对**：**在 tasks.md 的 Path Conventions 区域显式声明模块路径前缀。** 我们在 001 的实践中已经在 tasks.md 头部加了路径约定表——这是 Spec-Kit 用户必须做的第一件事。

### 局限 3：不支持实际代码生成

**症状**：Spec-Kit 管规划不管执行。tasks.md 给 AI 提供了清晰的指令清单，但最终写 Java 代码还是需要 Claude Code/Cursor 等 AI 编码工具。

**应对**：**Spec-Kit 做规划 + Claude Code 做执行。** 两者互补——Spec-Kit 产出 Tasks，Claude Code 按 Tasks 逐条实现。`/speckit-implement` 命令内嵌了这个流程，但实际体验中更高效的做法是直接打开 IDE，把 tasks.md 作为 prompt 的附件传给 Claude Code。

## 四、两阶段分界建议

### 主体开发阶段：用 Spec-Kit

**特征**：从零开始、多模块、架构决策未定型、需要结构化文档产出。

**工作流**（基于 001 的实际路径）：

```
/speckit-constitution  ← 喂入 CLAUDE.md 的 8 条原则
    ↓
/speckit-specify       ← 喂入功能描述
    ↓
/speckit-clarify       ← 解决 spec 中的模糊点
    ↓
/speckit-plan          ← 喂入技术方案（10 个决策 + 9 个模块）
    ↓
/speckit-tasks         ← 产出可执行的 Task 清单
    ↓
/speckit-analyze       ← 交叉验证 spec/plan/tasks 一致性
    ↓
Claude Code 逐 Task 实现  ← 把 tasks.md 当指令清单
```

**适用条件**（同时满足才走完整流程）：
- 新 Feature 涉及 ≥2 个 Maven 模块
- 新 Feature 需要新增 ≥3 个功能性需求
- 架构决策未在已有 plan.md 中覆盖

### 增量开发阶段：用手动提示词 + Claude Code

**特征**：已有可运行的 MVP、改动范围明确（修 bug、加 Tool、优化一个类）。

**工作流**：

```
1. 打开 IDE，选中要修改的文件/类
2. 写提示词：
   "在 ReActLoop.java 中加一个 hook——
   每次 Tool 执行完成后，在返回 LLM 之前，
   检查 ToolResult.content 是否超过 10000 字符，
   超过则自动截断并加 '...（已截断）' 后缀。
   保持现有审计写入逻辑不变。"
3. Claude Code 生成代码 → Review → 手动测试
4. 如果修改影响 spec/plan，手动更新对应文档
```

**适用条件**：
- 修改范围 ≤1 个 Maven 模块
- 不新增 Constitution 级别的约束
- 不改变数据模型（不新增表、不修改核心接口）

### 分界判断矩阵

| 场景 | 用什么 | 理由 |
|------|--------|------|
| 开始 Feature 001（ReAct Loop） | Spec-Kit | Greenfield，不确定架构，需要文档 |
| 在 ReActLoop 中加一个 hook | 手动提示词 | 单文件改动，不涉及架构 |
| 新增一个 Tool（如 `database_query`） | 手动提示词 | 实现 OryxTool 接口，不改变注册机制 |
| 开始 Feature 002（Memory 模块独立） | Spec-Kit | 新模块，新增接口，需要独立的 spec/plan |
| 修 bug：空返回重试逻辑不对 | 手动提示词 | 单文件逻辑修复 |
| 加 REST 端点（如 `/api/v1/stats`） | 手动提示词 | 在现有 ApiController 加方法 |
| 开始 Feature 003（Web 管理台） | Spec-Kit | 新的 Vue 3 前端项目，独立 spec/plan |

## 五、Spec-Kit 在 OryxOS 001 的实际数据

| 指标 | 001-react-loop-core 实际数据 |
|------|--------------------------|
| 全流程耗时 | ~30 分钟（constitution → analyze） |
| 生成文档 | 6 个（constitution + spec + plan + tasks + data-model + quickstart） |
| Task 数量 | 60 个，覆盖 17 FR + 6 SC |
| 覆盖率 | 95.5%（analyze 修复后 100%） |
| CRITICAL 问题 | 0 |
| 被纠正的问题 | 4 个（3 MEDIUM + 1 LOW） |
| 人工介入节点 | 2 个（clarify 3 轮 Q&A + analyze 修复） |

**结论**：Spec-Kit 在 OryxOS 的项目规模和约束复杂度下表现出色——60 个可执行 Task、0 个 CRITICAL 问题、17 条 FR 100% 覆盖。最大不足是模板对 Java 多模块的路径约定需要手动适配。

## 六、明确结论

**OryxOS 的 AI 辅助编程策略：Spec-Kit 做主体，手动提示词做增量。**

| 决策 | 选择 | 为什么 |
|------|------|--------|
| 主体开发用什么 | **Spec-Kit** | 9 个模块、10 个技术决策、8 条 Constitution——这个复杂度级别，不靠结构化规划 = 第三周返工。001 的实践证明 60 个 Task 零 CRITICAL 问题 |
| 增量开发用什么 | **手动提示词 + Claude Code** | Spec-Kit 的全流程对小改动太重。修一个 bug 不需要重新 clarify → plan → tasks |
| 什么时候切换 | **第一个 Feature 的 MVP 跑通之后** | Feature 001 交付 `oryxos chat` 可对话 → 之后的 Feature 增量走手动，全新 Feature 走 Spec-Kit |
| 绝不用的 | **纯 Vibe Coding** | 没有规划 = Constitution 8 条约束在第三轮对话后就被 AI "忘记"了。Vibe Coding 适合个人玩具，不适合有架构约束的工程项目 |

**三个不要**：
1. **不要妄想一个工具覆盖全流程。** Spec-Kit 管不好单行代码的 bug fix，手写提示词管不好 60 个 Task 的依赖排序。各用所长。
2. **不要跳过 Constitution Check。** 这是 Spec-Kit 最大的差异化价值——它强制你每次 plan 时对着 8 条原则逐条打勾。手写提示词没有这个机制。
3. **不要在 explore 阶段用 Spec-Kit。** 如果你还不知道 Feature 长什么样——先手动聊几轮搞清楚要做什么，再走 specify→plan。Spec-Kit 假设你已经想清楚了。

## 七、Spec-Kit 在 OryxOS 的完整实施流程

### 7.1 准备阶段的 3 个 Artifacts 写法

Spec-Kit 的 `/speckit-specify` → `/speckit-plan` → `/speckit-tasks` 三个命令不是凭空生成内容的。它们需要你把已有文档**喂进去作为输入**。以下是每个 artifact 的写法和输入来源。

#### Artifact 1：constitution.md

**作用**：8 条不可协商的原则。Plan 阶段逐条打勾，不通过 = 不进入实施。

**写法**：不是从零写——**直接从 CLAUDE.md 的"不可违背的原则"板块提取。**

```
CLAUDE.md §不可违背的原则（8条）
  每一条拆成: 原则名称 + MUST/NOT 声明 + Rationale
  技术栈约束单独成章（从 CLAUDE.md §技术栈提取）
  设计原则单独成章（从 CLAUDE.md §设计原则提取）
  治理规则（修订流程 + 版本策略 + 合规检查）
```

**产出案例**（001 实践）：219 行 `.specify/memory/constitution.md`，8 条 Core Principles + Technical Stack Constraints + Design Philosophy + Governance。全量从 CLAUDE.md 派生，零额外创作。

#### Artifact 2：spec.md

**作用**：User Stories + Functional Requirements + Success Criteria。Plan 和 Tasks 的输入。

**写法**：**把需求分析文档的"五个核心能力"转成 User Story 格式。**

```
需求分析 §一.五个功能模块
  每个模块 → 一个 User Story
  每个 User Story 包含: 一句话描述 + 优先级 + 独立测试标准 + Acceptance Scenarios

需求分析 §五.验收标准
  → Success Criteria（SC-001 ~ SC-006，去掉实现细节，只留可量化指标）

需求分析 §七.数据模型
  → Key Entities（提取实体名 + 核心属性，不写实现）
```

**关键规则**：
- User Story 只写 **What**，不写 **How**（How 是 Plan 的事）
- 每个 Story 必须有独立测试标准——"只实现这一个 Story，能不能单独验证"
- 优先级用 P1/P2/P3——P1 = 没有它系统跑不起来

**产出案例**（001 实践）：4 个 User Story (US1:CLI对话 P1 / US2:Tool调用 P1 / US3:Session持久化 P2 / US4:多Profile P3) + 17 FR + 6 SC。

#### Artifact 3：plan.md

**作用**：技术上下文 + Constitution Check + 项目结构 + 模块拆分。Tasks 的输入。

**写法**：**把技术方案的决策清单和模块架构转成 Plan 格式。**

```
技术方案 §一.10 个关键技术决策
  → Technical Context（Language/Dependencies/Storage/Testing/Performance/Constraints）

技术方案 §四.四层分层视图 + §六.9 个模块
  → Project Structure（Source Code 目录树）

技术方案 §一（每条决策的 Constitution 对齐）
  → Constitution Check 表格（逐条 PASS/FAIL + Notes）
```

**关键规则**：
- Technical Context 里不能有 NEEDS CLARIFICATION——如有，先解决再进 Plan
- Constitution Check 必须逐条打勾——不通过的不进 Tasks
- Project Structure 必须跟 Maven 模块结构一一对应——路径不准 = Tasks 文件路径全错

**产出案例**（001 实践）：Technical Context（Java 21 + Spring Boot 3.x + SQLite + 4 模块），Constitution Check 8 条全 PASS，Source Code 目录树 4 模块。

### 7.2 每个 Artifact 的内容来源映射

| Spec-Kit Artifact | 命令 | 内容从哪个文档提取 | 提取什么 |
|-------------------|------|------------------|---------|
| **constitution.md** | `/speckit-constitution` | `CLAUDE.md` §不可违背的原则（8条）+ §技术栈 + §模块结构 + §设计原则 | 8 条原则（含 Rationale + 代码示例）、9 项技术栈约束、7 条设计原则、治理规则 |
| **spec.md** | `/speckit-specify` | `02-需求分析.md` §一.五个功能模块 + §五.验收标准 + §七.数据模型 | 5 个 User Story（每个含 Acceptance Scenarios + Priority）、SC-001~006、6 个 Key Entities |
| **plan.md** | `/speckit-plan` | `03-技术方案.md` §一.10 个决策 + §四.四层架构 + §六.9 个模块 + §七.技术栈清单 | Technical Context、Constitution Check 表、Source Code 目录树、模块拆分 |
| **tasks.md** | `/speckit-tasks` | plan.md + spec.md（自动生成，需人工校验） | 按 User Story 分 Phase，每个 Task 带 ID + [P] 标记 + 文件路径 |
| **checklists/** | 自动生成 | spec.md | 质量检查清单（Content Quality / Requirement Completeness / Feature Readiness） |

### 7.3 5 个 User Story 的依赖关系与推进顺序

```
               US-1: 多Provider统一接入
               (无依赖，最先开始)
                      │
                      ▼
               US-2: ReAct循环
               (依赖US-1: 每轮迭代都要调LLM)
                      │
            ┌─────────┴─────────┐
            ▼                   ▼
   US-3: Agent配置化    US-4: Tool体系+沙箱
   (依赖US-2: 配置     (依赖US-2: Tool被
    经由ReAct加载)        ReAct调用执行)
            │                   │
            └─────────┬─────────┘
                      ▼
               US-5: Web+CLI双通道
               (依赖US-1~4全部)
```

**依赖逻辑逐条解释**：

| 依赖边 | 为什么 |
|--------|--------|
| US-1 → US-2 | ReAct Loop 每轮迭代调 `ProviderService.call()`。没有 Provider 接入 = ReAct Loop 调不到 LLM = Agent 没有大脑 |
| US-2 → US-3 | Agent Profile 通过 `AgentLoader` 加载后，由 ReAct Loop 的 `PromptBuilder` 注入 System Prompt。没有 ReAct Loop = Profile 只是存在内存里的配置，没有人消费它 |
| US-2 → US-4 | Tool 的执行由 ReAct Loop 中的 `ToolExecutor` 调度。没有 ReAct Loop = Tool 注册了但永远不会被调用 |
| US-3 与 US-4 并行 | AgentLoader（US-3）和 ToolRegistry（US-4）相互独立——前者读 AGENT.md 生成 Profile，后者扫描 @Tool 注解注册 OryxTool。两者不共享代码路径，可以并行开发 |
| US-1~4 → US-5 | Web API 和 CLI 是接入层——它们调 ReActLoop、SessionManager、AgentLoader、ToolRegistry。底层能力不跑通，接入层暴露的端点全是空壳 |

### 7.4 每个 User Story 的拆解表格

#### US-1：多 Provider 统一接入（Priority: P1，无依赖）

| 维度 | 内容 |
|------|------|
| **核心目标** | 底座能调通至少一个 LLM Provider；Provider 之间通过显式 Map 路由；支持 `${VAR}` 环境变量解析 |
| **涉及模块** | `oryxos-core`（ProviderService 接口 + Profile 模型）、`oryxos-provider`（ProviderServiceImpl 实现） |
| **Spec-Kit Task 类别** | Foundation Tasks（接口定义 + 模型 + 配置）+ Setup Tasks（Maven 模块 pom.xml）+ Implementation Tasks（ProviderServiceImpl + ConfigLoader） |

## 八、为什么增量阶段从 Spec-Kit 切换到手动提示词

Spec-Kit 的价值在**结构化规划**——把模糊需求变成可执行的 Task 清单。一旦 MVP 跑通，工作性质从"建骨架"变成"填血肉"。两种阶段的工作性质完全不同：

| 维度 | 主体开发阶段 | 增量开发阶段 |
|------|------------|------------|
| **工作性质** | 从零建骨架：定义接口、建模块、搭架构 | 在已有骨架上填血肉：加 Tool、修 bug、优化性能 |
| **单次改动范围** | 跨 2-4 个模块。每次改动涉及接口 + 实现 + 测试 | ≤1 个模块。通常单文件改动 |
| **架构影响** | 高。一个接口定义错了，下游 3 个模块返工 | 低。在已有接口框架内增加实现，不改变接口签名 |
| **文档变更** | 每次新增模块/接口 → spec/plan/data-model 要同步 | 大多数改动不需要改 spec——加一个 Tool 不改变功能边界 |
| **Constitution 风险** | 高。架构搭建阶段最容易违反 Constitution I/II/III（用 Spring AI 自动执行、靠类型扫描 Provider） | 中低。骨架已在 Constitution Check 中验证过，增量改动的"违规面"窄 |
| **Spec-Kit 开销** | 合理。30 分钟的全流程产出 60 个 Task，省去几百行规划文档的手写 | 不合理。改一个单行 bug 走 clarify→plan→tasks 3 个命令 = 浪费 10 分钟 |
| **最佳工具** | Spec-Kit（结构化命令链 + Constitution 硬门禁） | 手动提示词 + Claude Code（打开 IDE → 选中文件 → 一句话描述改动） |

**切换的判断标准**：当以下三个条件**同时满足**时，从 Spec-Kit 切换到手动提示词——

1. Feature 001 的 MVP 已跑通（`oryxos chat` 能对话 + 能调 Tool）
2. 所有核心接口（OryxTool / ProviderService / ToolRegistry）已稳定（连续 3 天无签名变更）
3. 后续改动范围 ≤1 个 Maven 模块且不新增 Constitution 级别约束

## 九、增量阶段的 6 步工作流

```
Step 1: 明确改动范围
  ├─ 这个改动涉及几个文件？
  ├─ 是否改变核心接口签名？
  └─ 决策: 走手动提示词 or 回 Spec-Kit

Step 2: 检查 Constitution 影响
  ├─ 打开 .specify/memory/constitution.md
  ├─ 这个改动会不会触碰 8 条中的任何一条？
  └─ 如果触碰 → 回 Spec-Kit 走完整 Constitution Check

Step 3: 写提示词
  ├─ 格式: [文件路径] + [要改什么] + [不改什么] + [Constitution 约束]
  └─ 示例: "在 ReActLoop.java 的 executeToolCalls() 方法中，
           每个 Tool 执行完成后加一个 hook——
           检查 ToolResult.content 是否超过 10000 字符，
           超过则自动截断并加 '...(已截断)' 后缀。
           不要改变现有的审计写入逻辑（Constitution V）。
           不要引入异步（Constitution VII）。"

Step 4: Claude Code 生成代码
  ├─ 让 AI 先展示要改的代码（不等执行）
  ├─ Review: 检查 Constitution 对齐、错误处理、边界条件
  └─ 通过后再让 AI 实际写入文件

Step 5: 验证 + 审计
  ├─ 编译: mvn clean compile
  ├─ 跑受影响的测试: mvn test -pl oryxos-core
  ├─ 手动验证: 启动 oryxos chat，触发改动的代码路径
  └─ 检查审计表: sqlite3 查 llm_calls/tool_invocations 是否正常

Step 6: 更新文档（按需）
  ├─ 如果改动改变了功能边界 → 更新 spec.md
  ├─ 如果改动新增了模块/接口 → 更新 plan.md
  ├─ 如果改动修复了一个已知风险 → 更新技术方案 §十三
  └─ 大多数 bug fix 不需要更新任何文档
```

## 十、与主体阶段 Artifacts 的对接方式

增量阶段不重新生成 Spec-Kit artifacts，但**已有的 artifacts 仍然是权威参考**。对接方式：

| Artifact | 在增量阶段的角色 | 什么时候更新 |
|----------|----------------|------------|
| **constitution.md** | **非协商原则。** 每次改动前对着 8 条自查——如果改动触碰任何 MUST/MUST NOT，改设计，不改原则 | 永远不改（除非通过正式 PR + review 流程） |
| **spec.md** | 功能边界参考。加新功能时先看 spec——如果新功能不在 spec 范围内，先更新 spec 再写代码 | 新增功能性需求时 |
| **plan.md** | 架构地图。改代码前先看 plan 的 Constitution Check 表——这个模块当初是怎么通过检查的 | 新增模块/接口/技术决策时 |
| **tasks.md** | 不再作为 Task 清单使用（那是主体阶段的用途）。但可以作为"还有什么事没做"的检查表 | 不更新（主体阶段完成后归档） |
| **data-model.md** | 数据库 schema 的权威参考。改 JPA Entity 前先核对 data-model | 新增表/字段时 |

**核心原则**：Constitution 是宪法——修改它需要走流程。Spec/Plan 是法律——可以修订但必须留痕。Tasks 是施工图——竣工后归档，不再维护。

## 十一、AI Agent 最容易跑偏 Constitution 的 8 个点

在多次 Spec-Kit 实践和 AI 辅助编程中，以下 8 个点是 AI Agent 最高频的 Constitution 违规模式。每一个都配了"AI 可能怎么写"和"正确的做法"。

| # | 违规点 | Constitution | AI 最容易怎么写（错误） | 正确做法 |
|---|--------|------------|---------------------|---------|
| 1 | **用 Spring AI 自动执行 Tool** | I, II | `chatClient.prompt(prompt).tools(tools).call().content()` — AI 看 Spring AI 文档学的就是这种写法，自动补全首选 | `chatModel.call(new Prompt(messages, options))` — 只用底层 API。Tool 执行在 `ReActLoop` 里手动调度 |
| 2 | **靠类型扫描发现 Provider** | III | `@Autowired List<ChatModel> chatModels` — AI 的习惯是用 Spring 的依注入自动收集所有 Bean | `Map<String, ChatModel> providerMap = Map.of("deepseek", deepseekModel, ...)` — 显式声明每一个 Provider |
| 3 | **把 AGENT.md 注册为 Tool** | IV | 在 `ToolRegistry` 扫描时把 `AGENT.md` 文件当 Tool 注册——AI 看到 "Tool" 和 "AGENT.md 有 frontmatter" 就联想注册 | AGENT.md 只由 `AgentLoader` 加载为 Profile。ToolRegistry 只扫描 `@Tool` 注解的 Bean 和 MCP 配置 |
| 4 | **审计写到日志文件而不是 SQLite** | V | `log.info("LLM call: {}", response)` — AI 看到结构化日志就认为"够了" | `llmCallRepository.save(new LlmCallEntity(...))` — 每次调用后同步写入数据库。SLF4J 日志是辅助，不是替代 |
| 5 | **引入 CompletableFuture 做异步** | VII | 在 ReActLoop 里 `CompletableFuture.supplyAsync(() -> chatModel.call(...))` — AI 看到"IO 等待"就本能地用异步 | 全程同步阻塞。Virtual Thread 自动在 IO 等待时释放载体线程。不需要任何异步工具 |
| 6 | **把 Tool 拆成多个 Maven 模块** | VIII | 创建 `oryxos-tool-file`、`oryxos-tool-shell`、`oryxos-tool-http` 三个模块——AI 喜欢"每个类别一个模块" | 所有内置 Tool + MCP Client 在一个 `oryxos-tool` 模块内。Tool 之间的内部实现可以分包，但不拆模块 |
| 7 | **用 `hibernate.ddl-auto=update` 迁移** | Tech Stack | `spring.jpa.hibernate.ddl-auto=update` — AI 看 Spring Boot 文档的默认配置 | 禁用 ddl-auto。表结构变更用手写 `schema.sql` 或 Flyway migration。SQLite 的 ALTER TABLE 极弱，依赖自动迁移 = 生产事故 |
| 8 | **在 System Prompt 里硬编码 API Key** | Config | 从 `application.yml` 直接读 `api_key: sk-xxx` — AI 看到配置文件有 api_key 字段就填进去 | `api_key: ${DEEPSEEK_API_KEY}` — 只在配置文件里写占位符，真值从环境变量读取。`ConfigLoader` 启动时解析 |

**预防措施**：每次 AI 生成代码后，对着这个表逐条检查。8 条全部通过 = 合并。任何一条不通过 = 退回修改。

## 十二、常见挑战与对策

| # | 挑战 | 症状 | 对策 |
|---|------|------|------|
| 1 | **AI 生成的代码"几乎对"但关键细节错** | ProviderServiceImpl 编译通过，但 Provider 用了 Bean 扫描而非显式 Map——Constitution III 违规，编译期看不出来 | Review 时对着 Constitution 8 条逐条检查。不只看"能不能编译"，更要看"有没有违反原则"。把 §十一的 8 个违规点做成 code review checklist |
| 2 | **Spec-Kit 生成的 Tasks 路径不匹配 Java 项目** | Tasks 默认用 `src/models/user.py` 这种路径格式，Java 多模块项目需要 `oryxos-core/src/main/java/com/oryxos/core/model/Profile.java` | 在 tasks.md 头部写 Path Conventions 区域，显式声明模块前缀。我们 001 实践已做——每个 Feature 的 tasks.md 都要做这一步 |
| 3 | **AI 在长对话中"忘记" Architecture 约束** | 第 1 轮 AI 记得"不用异步"，第 5 轮它建议"这里用 CompletableFuture 优化" | 每次新对话或长对话超过 10 轮时，重新粘贴 Constitution 8 条原则和 10 个技术决策作为 system prompt。不要让 AI 靠"记忆"遵守约束 |
| 4 | **Agent Profile 的环境变量解析失败** | `${DEEPSEEK_API_KEY}` 没被替换，API Key 为 null，LLM 调用失败——但错误信息是 "401" 而不是 "环境变量未设置" | `ConfigLoader` 在启动时遍历所有 `${...}` 占位符，逐个检查环境变量是否存在。缺失时明确报错："环境变量 DEEPSEEK_API_KEY 未设置，但被 Profile 'default' 引用" |
| 5 | **SandboxChecker 白名单太宽或太窄** | 太宽：`file.allowed_paths: ["/"]` = 裸奔。太窄：Agent 什么都干不了，用户体验差 | 默认白名单只包含 `.oryxos/` 和 `./workspace/`。Shell 默认只允许只读命令（ls/cat/grep）。用户需要更宽权限时自己改配置——我们不给默认全开 |
| 6 | **增量阶段的改动无意中打破了 Spec 的边界** | 给 ReActLoop 加了一个"自动重试 5 次"的 feature——但 clarify Q2 的结论是"重试 1 次"。新增 feature 覆盖了之前的决策 | 增量改动的 Step 2（检查 Constitution 影响）扩展为"检查 Spec 影响"——如果改动改变了用户可见行为，先看 spec.md 中的 FR/SC 是否已覆盖 |
| 7 | **MCP Server 超时拖死 ReAct Loop** | Agent 调了一个外部 MCP Tool，那个 MCP Server 挂了，TCP 连接等 2 分钟才超时——整个 ReAct Loop 卡住 | `ToolExecutor` 中每个 Tool 执行包 `Future.get(timeout)`。MCP Tool 默认超时 30s。超时后返回 ToolResult(success=false, error="Tool 执行超时 (30s)")——LLM 在下一轮迭代中尝试其他方法 |

### 如果只读一页

OryxOS 是 Java 原生的、企业私有部署的 Agent 统一底座。它不做最强的 Agent——它做让一群 Agent 可靠运行、可被审计、不锁任何云的操作系统级底座。

**为什么做**（业界调研）：OpenClaw 320K stars + Hermes 190K stars 验证了 Agent OS 品类的需求。但它们共同留下了三个空白——企业治理、底座产品形态、Java 生态缺位。57% 的企业已经在生产环境跑多步骤 Agent，但只有 21.9% 把 Agent 当作独立身份实体管理。Java 生态的 Agent 基建在快速成熟（Spring AI Alibaba、AI Fabric），但"装上就跑的 Agent 底座产品"是真空。

**做什么**（需求分析）：五个核心能力——多 Provider 接入、ReAct 循环、Agent 配置化、Tool 体系、Web+CLI 双通道。明确不做 10 件事——包括多租户、SSO、流式、可视化编排、Skill 市场、Agent 自进化。4 周 12 小时：W1 地基 → W2 心跳 → W3 手脚 → W4 通道。

**怎么做**（技术方案）：10 个关键技术决策——自实现 ReAct Loop、Spring AI 只做协议层、Virtual Thread 同步阻塞、SQLite 零依赖、OryxTool 统一接口、Picocli CLI、SandboxChecker 白名单、AGENT.md 文件配置、审计同步写 SQLite、6 个 Maven 模块依赖倒置。四层架构：接入层 → 引擎层 → 能力层 → 基础层。扩展阶段加新能力只加模块不改核心。

**怎么用 AI 做**（编程指南）：主体开发用 Spec-Kit 做结构化规划（constitution → specify → plan → tasks），增量开发用手动提示词 + Claude Code。Constitution 8 条原则是所有阶段的非协商门禁。AI 最容易在 8 个具体点上跑偏——每次 code review 对着检查表逐条验证。

### 四个文档之间的关系不是并列，是递进

每一份文档的结论是下一份文档的输入。不是四份独立报告——是一根链条上的四个环节。拆开任何一环，后面的推理就失去了地基。这正是 OryxOS 本身的设计哲学：**底座优先于 Agent。** 文档体系也是底座——它让 AI 和人类在同一个约束框架内工作，不跑偏、不推倒重来、不靠运气。
