# 技术方案：OryxOS 的架构决策与模块设计

> **本文定位**：回答"怎么实现"——以 10 个关键技术决策为主线，每个决策给出明确选择和理由，不模糊。
> **前置文档**：[业界调研](./01-业界调研.md) → [需求分析](./02-需求分析.md)
> **下一份文档**：编程指南
> **核心约束**：4 周 × 每周 3 小时 = 12 小时总投入，所有设计在此约束内。

## 一、10 个关键技术决策

### 决策 1：LLM 调用方式 — 用什么调大模型？

**决策点**：OryxOS 怎么调用各家 LLM Provider？自建 HTTP Client 直接调 API，还是用框架？

**选择**：**Spring AI Alibaba 做协议适配层，但只用 `ChatModel.call(Prompt)` 底层 API，不用 `ChatClient` 的自动 Tool 执行。**

**为什么**：
1. 每家 LLM Provider 的 API 格式不同（OpenAI/Anthropic/Gemini/DeepSeek）——Spring AI 吸收这些差异，不需要自己写 5 套请求构造和响应解析。
2. `ChatModel.call(Prompt)` 是最底层 API，返回原始 `ChatResponse`，不触发任何自动行为——OryxOS 自己解析 Tool Call、自己调度执行，完全掌控循环逻辑。
3. 禁掉自动 Tool 执行是 Constitution Principle II 的硬要求——一旦用了 `ChatClient.prompt().tools().call()`，Tool 被调两次且无法阻止。

**备选方案**：直接用 OkHttp/HttpClient 调各家 API → 放弃了协议适配层，每个 Provider 要手写请求构造、响应解析、流式处理，工作量大且容易出错。Spring AI 的协议适配是唯一正确的复用点。

---

### 决策 2：ReAct Loop 实现方式 — Agent 的"心跳"谁写？

**决策点**：Agent 的核心决策循环（Reasoning → Acting → Observation → 循环）用什么实现？Spring AI 的 Agent 抽象，还是自己写？

**选择**：**自实现。一个约 60-80 行的 while 循环，不依赖任何第三方 Agent 执行器。**

**为什么**：
1. ReAct Loop 是 OryxOS 最核心的控制点——审计在哪写、错误怎么处理、循环何时终止——每一个决策都必须在自己的代码里，不能在第三方黑盒里。
2. Spring AI 的 Agent 抽象（`ToolRunController`、`ChatClient` 自动执行）会接管 Tool 调度——这正是 Constitution Principle I 禁止的。
3. 60-80 行 Java 代码的量不值得引入一个框架。自己写 = 完全可控 + 零黑盒 + 未来定制零摩擦。

**备选方案**：Spring AI `ChatClient.prompt().tools().call()` → 自动执行 Tool → Tool 被调两次（Spring AI 执行一次 + OryxOS `ToolExecutor` 执行一次），且无法在 Tool 执行前后插入审计逻辑。**这是 Constitution 明确禁止的做法。**

---

### 决策 3：并发模型 — 同步还是异步？

**决策点**：ReAct Loop 内部有大量 IO 等待（LLM HTTP 调用、Tool 执行），用什么并发模型？传统的线程池 + CompletableFuture，还是 Reactive 流式？

**选择**：**全程同步阻塞 + Java 21 Virtual Thread。不引入任何异步编程模型。**

**为什么**：
1. Virtual Thread 让同步代码在 IO 等待时自动释放载体线程——一个 `ChatModel.call()` 的 HTTP 阻塞在 Virtual Thread 上几乎零成本，不需要写 callback/CompletableFuture/Mono。
2. 同步代码可读性、可调试性远超异步。ReAct Loop 的业务逻辑天然是顺序的（思考 → 执行 → 观察 → 再思考），用同步表达最自然。
3. 12 小时总投入的环境中，引入 Reactor/WebFlux 的调试复杂度（堆栈不可读、上下文丢失）是致命的生产力杀手。

**备选方案**：Spring WebFlux + Reactor → 异步非阻塞，但调试极难、堆栈不可读、学习曲线陡。**单用户 CLI 场景不需要异步吞吐，异步是过度设计。**

---

### 决策 4：持久化方案 — 对话和审计存哪？

**决策点**：Session 数据、LLM 调用记录、Tool 执行记录存哪里？PostgreSQL？MySQL？还是更轻的方案？

**选择**：**SQLite + Spring Data JPA。表结构用 `schema.sql` 显式维护，禁用 `hibernate.ddl-auto=update`。**

**为什么**：
1. SQLite 是零依赖嵌入式数据库——不需要装数据库服务、不需要配置连接池、不需要运维。`oryxos init` 创建一个 `.db` 文件即可。这对"装上就跑"的产品体验是核心。
2. Spring Data JPA 提供标准的 Repository 抽象——如果将来要换 PostgreSQL，只需要换 dialect 和驱动，Repository 接口一行不改。
3. SQLite 的 `ALTER TABLE` 极弱——所以用 `schema.sql` 显式建表，迁移时手动写 DDL 或引入 Flyway。**不依赖 Hibernate 自动 DDL** 是 Constitution 明确要求的。

**备选方案**：PostgreSQL → 太重。需要单独安装、配置、运维——跟"java -jar 就跑"的产品目标冲突。核心阶段单用户场景不需要 PG 的并发能力。扩展阶段如果真需要，JPA 接口不变，换驱动即可。

---

### 决策 5：Tool 注册机制 — Agent 怎么知道有哪些 Tool？

**决策点**：Tool 怎么注册到 OryxOS？LLM 怎么知道有什么 Tool 可用？谁负责把 Tool 的描述和参数格式告诉 LLM？

**选择**：**OryxTool 统一接口 + ToolRegistry 集中注册 + Spring AI 的 `@Tool` 注解做 JSON Schema 生成。**

**为什么**：
1. `OryxTool` 接口（getName/getDescription/getParametersJsonSchema/execute）是所有 Tool 的唯一抽象——内置 Tool、MCP Tool、Plugin Tool 全部适配到这个接口。
2. ToolRegistry 提供 `toFunctionCallingFormat()` 方法——基于 Spring AI 的 Schema 生成能力，把已注册 Tool 列表转为 LLM Function Calling 格式的 JSON。
3. 复用 Spring AI 的 Schema 生成（这是 Constitution Principle II 允许的两件事之一），但不让 Spring AI 执行 Tool。

**备选方案**：手写 JSON Schema 字符串 → 每个 Tool 开发者都要懂 JSON Schema 格式，容易出错。Spring AI 的 `@Tool` 注解自动从方法签名生成 Schema，正确且零成本。

---

### 决策 6：HTTP 服务层 — Web API 怎么提供？

**决策点**：OryxOS 的 REST API 用什么框架提供？Spring MVC，还是 WebFlux？

**选择**：**Spring MVC + Tomcat + Virtual Thread。10 个端点，同步 Controller，统一 JSON 响应体。**

**为什么**：
1. 跟决策 3（同步模型）一致——Controller 方法同步返回，Virtual Thread 自动处理 IO 等待。
2. Spring MVC 是最成熟的 Java Web 框架，调试方便、社区资料多、团队学习成本接近于零。
3. 10 个端点的规模不需要 WebFlux 的异步吞吐。12 小时内写 10 个同步 Controller 远快于 10 个 Reactive Handler。

**备选方案**：Spring WebFlux → 跟决策 3 一样，异步模型引入了不必要的复杂度。核心阶段不存在需要异步非阻塞才能解决的并发问题。

---

### 决策 7：Sandbox 策略 — Agent 调 Tool 怎么保证安全？

**决策点**：Agent 调 `shell`、`read_file`、`http_get` 时，怎么防止它做不该做的事？用 Java SecurityManager 还是别的？

**选择**：**SandboxChecker + 三类白名单（路径/命令/域名）。不用 SecurityManager。**

**为什么**：
1. `SecurityManager` 在 JDK 17 废弃、JDK 21 已不可用——用它是逆着 JDK 方向走，未来每个版本都可能 break。
2. 白名单模型简单、可审计、可配置：文件操作 → 路径白名单、Shell → 命令首 token 白名单、HTTP → 域名通配符白名单。白名单之外 = 拒绝。
3. 核心阶段先实现白名单校验逻辑，白名单配置硬编码或从 `application.yml` 读取。后续扩展阶段可以由管理员通过 Web 管理台动态配置。

**备选方案**：SecurityManager → 已废弃，不可用。容器沙箱（Docker/gVisor）→ 太重，核心阶段不引入容器依赖。

---

### 决策 8：Agent 配置存储格式 — Agent 怎么定义？

**决策点**：Agent 的配置（名称、模型、Tool、渠道、System Prompt）存在哪里？数据库表？YAML 文件？还是别的方式？

**选择**：**一个目录 = 一个 Agent。`AGENT.md`（YAML frontmatter + Markdown 正文）定义 Agent 的全部配置。**

**为什么**：
1. 文件系统是唯一不需要额外工具的"数据库"——创建 Agent = 创建一个文件夹 + 写一个 Markdown 文件。不需要 Web 管理台也能操作。
2. YAML frontmatter 可被任何文本编辑器打开、被 git 版本管理、被 CI 检查——对开发者友好。正文是 Markdown——对非开发者可读。
3. 底座启动时自动扫描 `agents/` 目录，`AgentLoader.deriveProfile(dir)` 解析 frontmatter → `Profile` 对象。热加载只需重新扫描目录。

**备选方案**：数据库存 Profile → 需要 Web 管理台才能创建 Agent，失去了"文件即配置"的简单性。git 版本管理也做不到。**文件系统是 Agent 配置的最简可行存储。**

---

### 决策 9：审计策略 — 审计怎么落、什么时候落？

**决策点**：LLM 调用和 Tool 执行的审计记录，用日志文件还是数据库？调用后就立即写，还是攒一批再写？

**选择**：**SQLite 同步写入，每次 LLM 调用/Tool 执行完成后立即写一条记录。不依赖日志文件。**

**为什么**：
1. 结构化落库（`llm_calls` + `tool_invocations` 两张表）意味着审计数据可以被查询、统计、关联。日志文件是字符串——查询效率为零，合规审查需要导出再分析。
2. 同步写入 = 不丢数据。调用后立即 INSERT，如果写入失败，调用本身可以被标记为失败。异步攒批 = 进程崩溃丢一批审计记录。
3. Constitution Principle V 要求 Day One 写入审计表——"日志够了"是明确禁止的借口。

**备选方案**：SLF4J 结构化日志 → 日志文件没有查询能力。扩展阶段如果需要从审计数据出报表、做合规审查，从日志反解析的成本远高于一开始就落库。

---

### 决策 10：项目结构 — 几个 Maven 模块？怎么拆？

**决策点**：OryxOS 的代码怎么拆模块？一个巨无霸 jar 还是多模块？拆几个？

**选择**：**6 个 Maven 模块。核心阶段用 4 个（core/provider/tool/channel-cli/boot），oryxos-web 在 W4 加入。**

**为什么**：
1. 模块间通过 `oryxos-core` 里的接口解耦——每个下游模块依赖 core 的接口，不直接依赖彼此的实现。这是依赖倒置：core 定义契约，下游实现。
2. 新增 Channel 或 Tool 只加新模块，不改 core——符合开闭原则。未来加 `oryxos-channel-wecom` 或 `oryxos-tool-mcp` 时，只加模块不改旧代码。
3. 禁止模块间循环依赖——core 不依赖任何其他模块，provider 不依赖 tool，tool 不依赖 channel。

```
oryxos/
├── oryxos-core/         ← 接口 + 模型 + ReActLoop + PromptBuilder
│                         (所有模块依赖它，它不依赖任何人)
├── oryxos-provider/     ← ProviderServiceImpl (依赖 core)
├── oryxos-tool/         ← 内置 Tool + MCP Client + SandboxChecker (依赖 core)
├── oryxos-channel-cli/  ← Picocli + JLine (依赖 core)
├── oryxos-web/          ← REST API (依赖 core)
└── oryxos-boot/         ← Spring Boot 启动 + 自动配置 (依赖所有人)
```

**备选方案**：单个大模块 → 失去模块边界，循环依赖不可避免。Tool 代码不小心调了 CLI 代码 = 编译也发现不了。Constitution 允许模块按需演进，但不允许循环依赖。

## 二、决策总结矩阵

| # | 决策点 | 选择 | 一句话理由 |
|---|--------|------|----------|
| 1 | LLM 调用 | Spring AI `ChatModel.call()` 底层 API | 复用协议适配，禁掉自动执行 |
| 2 | ReAct Loop | 自实现 while 循环（~70行） | 核心控制点必须在自己的代码里 |
| 3 | 并发模型 | Virtual Thread + 同步阻塞 | 同步可读 + VT 免费异步吞吐 |
| 4 | 持久化 | SQLite + schema.sql 显式建表 | 零依赖，"java -jar 就跑" |
| 5 | Tool 注册 | OryxTool 接口 + ToolRegistry + Spring AI Schema | 统一抽象 + 复用 Schema 生成 |
| 6 | HTTP 服务 | Spring MVC + Tomcat + VT | 跟同步模型一致，零学习成本 |
| 7 | Sandbox | SandboxChecker + 三类白名单 | SecurityManager 已废弃，白名单简单可审计 |
| 8 | Agent 配置 | `AGENT.md`（YAML frontmatter + Markdown） | 文件即配置，git 可管理 |
| 9 | 审计策略 | SQLite 同步写入，调完即写 | 结构可查询，同步不丢数据 |
| 10 | 模块结构 | 6 个 Maven 模块，core 放接口 | 依赖倒置，禁止循环依赖 |

## 三、跨模块接口契约

以下三个接口放 `oryxos-core`，是模块解耦的基石：

### OryxTool

```java
package com.oryxos.core.tool;

public interface OryxTool {
    String getName();
    String getDescription();
    String getParametersJsonSchema();
    ToolResult execute(JsonNode input);
}

public record ToolResult(
    String toolCallId,
    boolean success,
    String content,
    String errorMessage
) {}
```

### ProviderService

```java
package com.oryxos.core.provider;

public interface ProviderService {
    ChatResponse call(List<Message> messages,
                      List<OryxTool> tools,
                      Profile profile);
    boolean isAvailable(String providerName);
    List<String> listProviders();
}
```

### ToolRegistry

```java
package com.oryxos.core.tool;

public interface ToolRegistry {
    void register(OryxTool tool);
    void unregister(String toolName);
    OryxTool get(String toolName);
    List<OryxTool> listAll();
    List<OryxTool> listForProfile(Profile profile);
    String toFunctionCallingFormat(List<OryxTool> tools);
}
```

### 四层职责

| 层 | 职责 | 包含模块 | 一句话 |
|----|------|---------|--------|
| **接入层** | 用户和外部系统怎么跟 OryxOS 交互 | channel-cli, web | 适配不同"对话入口"，对引擎层统一发 Message |
| **引擎层** | Agent 运行时内核——决策循环、Prompt 组装、Tool 调度 | core（ReActLoop, PromptBuilder, ToolExecutor, SessionManager, AgentLoader, ToolRegistry） | 所有 Agent 共享的执行环境。加新能力不改这层 |
| **能力层** | 可插拔的功能模块——LLM Provider、Tool、Memory、Sandbox | provider, tool（未来：memory, sandbox, a2a） | 每个模块通过实现 core 的接口接入。加新能力 = 加新模块 |
| **基础层** | 共享的数据模型、持久化、配置、启动 | core 中的 model 包、boot | 所有模块的共同地基 |

### 分层核心规则

1. **依赖方向**：接入层 → 引擎层 → 能力层 → 基础层。上层依赖下层，下层不感知上层。
2. **能力层模块平级**：provider 不依赖 tool，tool 不依赖 provider。都只依赖 core 中的接口。
3. **扩展阶段加新能力**：只加新模块（如 `oryxos-sandbox`、`oryxos-memory`、`oryxos-a2a`），不改 core 接口。

## 五、五个核心能力 → 模块映射

| 核心能力 | 涉及模块 | 分布层 | 关键类 |
|---------|---------|--------|--------|
| **1. 多 Provider 接入** | core（ProviderService 接口）+ provider（实现） | 引擎层定义契约，能力层实现 | `ProviderService`, `ProviderServiceImpl`, `FunctionCallingAdapter` |
| **2. ReAct 循环** | core | 引擎层 | `ReActLoop`, `PromptBuilder`, `ToolExecutor` |
| **3. Agent 配置化** | core | 引擎层 | `AgentLoader`, `ConfigLoader`, `Profile` |
| **4. Tool 体系 + 沙箱** | core（OryxTool 接口 + ToolRegistry）+ tool（内置 Tool + MCP Client + SandboxChecker） | 引擎层定义契约，能力层实现 | `OryxTool`, `ToolRegistry`, `ToolExecutor`, `FileTools`, `ShellTools`, `HttpTools`, `SandboxChecker` |
| **5. Web + CLI** | channel-cli（CLI）+ web（REST API） | 接入层 | `CliChannel`, `CliCommand`, `ApiController`, `GlobalExceptionHandler` |

**关键设计**：Core 只放接口和引擎。任何具体能力（一个 Tool、一个 Provider、一个 Channel）都是"能力层模块实现 core 接口"。

## 六、9 个 Maven 模块：名称、职责与技术要点

### 模块 1：oryxos-core

**职责**：所有模块的共同地基。放接口定义、核心模型、引擎实现。不依赖任何其他模块。

**技术要点**（≤200 字）：
- `model/` 包：Profile、Session、Message、ToolResult、ToolCallData——纯 POJO/Record，无框架依赖。
- `loop/` 包：ReActLoop 是核心类，约 70 行 while 循环。同步阻塞 + Virtual Thread。每次迭代写审计。
- `prompt/` 包：PromptBuilder 负责四段式组装——System Prompt + 对话历史 + Tool 列表 + 用户消息。截断逻辑在 `maxHistoryTurns` 生效。
- `tool/` 包：OryxTool 接口（3 个方法 + execute）、ToolRegistry 接口、ToolExecutor（查 Registry → 执行 → 返回 ToolResult）。SandboxChecker 接口放这层，具体白名单逻辑在 tool 模块实现。
- `agent/` 包：AgentLoader.deriveProfile() 用 SnakeYAML 解析 AGENT.md frontmatter，`${VAR}` 环境变量用正则替换。
- `session/` 包：SessionManager 负责 create/save/load，调 SessionRepository。
- `config/` 包：ConfigLoader 读 application.yml，校验必填项，缺项报错不静默。

### 模块 2：oryxos-provider

**职责**：LLM Provider 的具体实现。显式维护 `Map<String, ChatModel>`。

**技术要点**（≤200 字）：
- ProviderServiceImpl 维护 `Map<String, ChatModel>`——key 是 Provider 名称（"deepseek"/"qwen"/"kimi"），value 是 Spring AI 的 ChatModel 实例。
- 每个 ChatModel 的创建走 Builder：endpoint、API Key（从环境变量读取）、超时配置。
- 不靠 Spring 容器类型扫描——所有 Provider 的 Bean 类型都是 ChatModel，类型扫描无法区分。显式 Map 是唯一确定性路由方式。
- FunctionCallingAdapter：ChatResponse → 提取 `AssistantMessage` 中的 `ToolCall` 列表 → 转为 OryxOS 的 ToolCallData 列表。
- `isAvailable()` 方法：启动时发一个最小化请求验证连通性，结果缓存供 `oryxos status` 展示。

### 模块 3：oryxos-tool

**职责**：内置 Tool 实现 + MCP Client + SandboxChecker。所有 Tool 通过实现 OryxTool 接口注册。

**技术要点**（≤200 字）：
- 内置 Tool（9 个）：FileTools（read/write/list，用 `java.nio.file`）、ShellTools（`ProcessBuilder`，超时 30s 可配）、HttpTools（`java.net.http.HttpClient`，支持 GET/POST）、MemoryTools（读写 MEMORY.md 文件）、NotifyTools（Webhook 推送）。
- ToolRegistryImpl：维护 `Map<String, OryxTool>`。启动时扫描 `@Tool` 注解的 Spring Bean + 手动注册的内置 Tool。`toFunctionCallingFormat()` 用 Spring AI 的 Schema 生成能力转 FC JSON。
- MCP Client：用 Spring AI 的 MCP 支持，通过 JSON-RPC 转发到外部 MCP Server。MCP Tool 注册时包装为 OryxTool 实现。
- SandboxChecker：三类白名单——`file.allowed_paths`（PathMatcher）、`shell.allowed_commands`（首 token 比对）、`http.allowed_domains`（通配符匹配）。白名单从 application.yml 加载。白名单之外 → 抛 SandboxException。

### 模块 4：oryxos-channel-cli

**职责**：Picocli 命令行入口 + JLine 交互式对话循环。

**技术要点**（≤200 字）：
- CliCommand：Picocli `@Command` 注解，定义 12 个子命令（init/chat/serve/status/profile/provider/tool/session）。子命令通过 `CommandLine.run()` 分发。
- CliChannel：JLine `LineReader` 实现 readline 循环。读一行 → 调 ReActLoop → 打印回复 → 循环。`/exit` 和 Ctrl+C 触发 Session 保存 + 进程退出。
- 空白输入检测：`input.trim().isEmpty()` → 不调 ReActLoop，直接重新显示 prompt。
- 输出格式化（CliFormatter）：Tool 调用进度显示"🔧 正在调用 read_file..."，超时/错误用红色高亮。
- 不依赖 Picocli Spring Boot Starter（历史上兼容性问题多），直接 `new CommandLine(new CliCommand()).execute(args)`。

### 模块 5：oryxos-web

**职责**：REST API 10 个端点 + 全局异常处理 + 统一 JSON 响应体。

**技术要点**（≤200 字）：
- ApiController：`@RestController` + `@RequestMapping("/api/v1")`。每个端点方法 ≤15 行——参数校验 → 调 Core 服务 → 包装响应体。
- 统一响应体：`ApiResponse<T>` 记录（code, message, data, timestamp）。成功用 200/201，失败用统一错误码枚举。
- GlobalExceptionHandler：`@RestControllerAdvice`。SandboxException → 403，ProfileNotFoundException → 404，通用 Exception → 500。所有异常返回 `{"code":"...","message":"人类可读描述"}`。
- Spring MVC 同步 Controller。Tomcat + Virtual Thread 处理并发请求。不做认证（核心阶段假设内网）。

### 模块 6：oryxos-boot

**职责**：Spring Boot 启动 + 自动装配 + 配置文件 + 数据库初始化。

**技术要点**（≤200 字）：
- OryxosApplication：`@SpringBootApplication` + `main()` 中调 Picocli CommandLine.run()。
- OryxosAutoConfiguration：`@Configuration` + `@Bean` 定义——扫描 agents/ 目录 → 创建所有 Profile → 构造 ProviderService → 构造 ToolRegistry → 构造 ReActLoop。全部单例。
- application.yml：`spring.threads.virtual.enabled=true`、SQLite 数据源配置、Provider 列表、白名单配置。
- schema.sql：Spring Boot 自动执行（`spring.sql.init.mode=always`），创建 sessions/tool_invocations/llm_calls 三张表。
- logback-spring.xml：JSON 格式输出，INFO 级别，审计日志单独 marker。

### 模块 7-9（扩展阶段预留）

| 模块 | 职责 | 激活时机 |

### 9.1 ReAct Loop 的算法步骤

ReAct Loop 是 OryxOS 最核心的运行时机制——它是 Agent 的"心跳"。

```
┌─────────────────────────────────────────────────────┐
│                  ReAct Loop 完整流程                  │
└─────────────────────────────────────────────────────┘

用户消息进入
    │
    ▼
┌─────────────────┐
│  iteration = 0   │
└────────┬────────┘
         │
         ▼
╔═══════════════════════════════════════════════════════╗
║              迭 代 循 环 开 始                          ║
╚═══════════════════════════════════════════════════════╝
         │
         ▼
┌─────────────────────────────────────┐
│ Step 1: PromptBuilder.assemble()     │
│ ┌─────────────────────────────────┐ │
│ │ [System Prompt]                 │ │
│ │   AGENT.md 正文 + Bootstrap 文件│ │
│ │ + [长期记忆]                     │ │
│ │   MEMORY.md 全文 (≤4000 字)     │ │
│ │ + [对话历史]                     │ │
│ │   最近 max_history_turns 轮      │ │
│ │ + [可用 Tool 列表]               │ │
│ │   ToolRegistry.toFCFormat()     │ │
│ │ + [用户消息]                     │ │
│ └─────────────────────────────────┘ │
└────────────────┬────────────────────┘
                 │
                 ▼
┌─────────────────────────────────────┐
│ Step 2: ProviderService.call()       │
│   → LLM HTTP 请求                    │
│   → 写入 llm_calls 审计表            │
│   → 检查超时？                       │
│       ├─ 超时 → 直接报错给用户 (停)   │
│       └─ 正常 → 继续                  │
└────────────────┬────────────────────┘
                 │
                 ▼
┌─────────────────────────────────────┐
│ Step 3: 检查返回内容                  │
│   ├─ 有 text 内容 + 无 toolCalls     │
│   │   → 这是最终回复 → 返回给用户 (停) │
│   │                                  │
│   ├─ 有 toolCalls[]                  │
│   │   → 进入 Step 4                  │
│   │                                  │
│   └─ 空内容 (无text 无toolCalls)     │
│       → 重试1次? (告知LLM重新生成)     │
│       → 仍空 → 报错给用户 (停)        │
└────────────────┬────────────────────┘
                 │ (有 toolCalls)
                 ▼
┌─────────────────────────────────────┐
│ Step 4: Tool 执行链路                │
│                                     │
│   for each toolCall (顺序执行):      │
│   ┌─────────────────────────────┐   │
│   │ 4a. 解析: toolName, args    │   │
│   │ 4b. ToolRegistry.get(name)  │   │
│   │     ├─ 找到 → 继续          │   │
│   │     └─ 未找到 → ToolResult  │   │
│   │         (success=false)     │   │
│   │ 4c. 参数校验:               │   │
│   │     args vs getParamsSchema │   │
│   │     ├─ 匹配 → 继续          │   │
│   │     └─ 不匹配 → ToolResult  │   │
│   │         (success=false,     │   │
│   │          error="参数不匹配") │  │
│   │ 4d. SandboxChecker.check()  │   │
│   │     ├─ 白名单通过 → 继续    │   │
│   │     └─ 不通过 → ToolResult  │   │
│   │         (success=false,     │   │
│   │          error="沙箱拦截")   │  │
│   │ 4e. OryxTool.execute(args) │   │
│   │     → ToolResult            │   │
│   │ 4f. 写入 tool_invocations   │   │
│   │     审计表                   │   │
│   └─────────────────────────────┘   │
│                                     │
│   所有 Tool 执行完毕                  │
│   → 每个 ToolResult 转为 ToolMessage │
│   → 追加到对话历史                    │
└────────────────┬────────────────────┘
                 │
                 ▼
┌─────────────────────────────────────┐
│ Step 5: iteration++                  │
│   ├─ iteration < maxIterations       │
│   │   → 回到 Step 1 (下一轮迭代)      │
│   └─ iteration >= maxIterations      │
│       → 返回已有信息 + "未完成"原因    │
│       → (停)                          │
└─────────────────────────────────────┘
```

**关键设计点**：

| 步骤 | 设计要点 | 对应 Constitution/需求 |
|------|---------|---------------------|
| Step 1 | PromptBuilder 四段组装。记忆截断 4000 字。Tool 列表只含当前 Agent 启用的 Tool | 需求：Agent 配置化（每个 Agent 独立 Tool 集） |
| Step 2 | ProviderService 封装 Spring AI `ChatModel.call()`。超时不重试 | Clarify Q3 结论 |
| Step 3 | 空返回重试 1 次。Tool Call 解析用 Spring AI 的 `AssistantMessage.getToolCalls()` | Clarify Q2 结论 |
| Step 4 | Tool 顺序执行（不并行——Clarify A1）。每次执行前过 Sandbox。每次执行后写审计 | Constitution V（审计 Day One） |
| Step 5 | maxIterations 跨 Tool Call 计数（不是跨"用户消息"）。达到上限返回部分结果 | FR-010 |

### 9.2 Memory 三层记忆的统一门面

OryxOS 采用三层记忆设计。核心阶段实现前两层（会话记忆 + 长期记忆），第三层（情景记忆）留到扩展阶段。

```
┌─────────────────────────────────────────────────────┐
│                 MemoryService (门面)                  │
│                                                     │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐ │
│  │ 会话记忆     │  │ 长期记忆     │  │ 情景记忆     │ │
│  │ (W2 实现)   │  │ (W3 实现)   │  │ (扩展阶段)   │ │
│  │             │  │             │  │             │ │
│  │ 存储:       │  │ 存储:       │  │ 存储:       │ │
│  │ Session.    │  │ MEMORY.md   │  │ SQLite 表   │ │
│  │ messages_   │  │ 文件系统     │  │             │ │
│  │ json        │  │             │  │ 内容:       │ │
│  │             │  │ 操作:       │  │ 每次任务    │ │
│  │ 生命周期:   │  │ save_memory │  │ 的决策链    │ │
│  │ 一次对话    │  │ recall_     │  │ 和修改      │ │
│  │ 内有效      │  │ memory     │  │ 的文件      │ │
│  └─────────────┘  └─────────────┘  └─────────────┘ │
└─────────────────────────────────────────────────────┘
```

**MEMORY.md 文件结构**：

```markdown
# OryxOS 长期记忆

> 此文件由 Agent 通过 save_memory Tool 自动写入，请勿手动编辑。
> 最大长度 4000 字，超出时自动截断保留最近内容。

## 用户偏好

- 用户叫张三，偏好使用 Spring Boot 做后端开发
- 用户喜欢简洁的代码风格，不要过度设计

## 项目背景

- 当前项目是 OryxOS，一个 Java 企业级 Agent 底座
- 使用 Java 21 + Spring Boot 3.x + SQLite

## 关键决策

- 2026-07-15: ReAct Loop 采用自实现方案，不用 Spring AI 自动执行
- 2026-07-20: 持久化选择 SQLite 而非 PostgreSQL（零依赖优先）
```

**写入规则**：
- 通过 `save_memory` Tool 追加文本到对应分区（Agent 自行判断该写到哪个 `##` 分区下）
- MemoryService 在每次写入后检查总字数，超过 4000 字从头部截断
- 分区标题（`## 用户偏好`、`## 项目背景`、`## 关键决策`）由系统预设，Agent 只能追加到现有分区或创建新分区

**两个内置 Memory Tool**：

| Tool | 功能 | 实现 |
|------|------|------|
| `save_memory` | 追加一条记忆到 MEMORY.md。参数：`category`（分区名）、`content`（内容）。返回：成功/失败 | `Files.writeString()` 追加模式。写入后 `LongTermMemory.truncateIfNeeded()` 检查字数 |
| `recall_memory` | 关键词检索 MEMORY.md。参数：`query`（关键词）。返回：匹配的段落 | 简单子串匹配（核心阶段）。扩展阶段升级为向量检索（SQLite FTS5 或 pgvector） |

**注入 System Prompt 的时机**：

```
ReAct Loop Step 1 → PromptBuilder.assemble():
  1. 读 MEMORY.md 全文
  2. 如果字数 > 4000 → 只取最后 4000 字
  3. 插入到 System Prompt 之后、对话历史之前
  4. 格式: "<memory>\n{MEMORY.md 内容}\n</memory>"
```

**核心阶段 vs 扩展阶段的分界**：

| 维度 | 核心阶段 (W3) | 扩展阶段 |
|------|-------------|---------|
| 存储 | MEMORY.md 文件 | SQLite 表 + 向量索引 |
| 检索 | 子串匹配 | FTS5 全文搜索 / 向量相似度 |
| 截断 | 4000 字截头 | 智能摘要 + 过期清理 |
| 分区 | 3 个预设分区 | Agent 动态创建分区 |

**Sandbox 接口设计**：

```java
// 接口放 oryxos-core，实现放 oryxos-tool
public interface SandboxChecker {
    /**
     * 校验 Tool 执行请求是否在白名单内。
     * @return SandboxVerdict: ALLOWED / DENIED + reason
     */
    SandboxVerdict check(OryxTool tool, JsonNode arguments);

    /** 文件操作白名单校验 */
    boolean isPathAllowed(Path targetPath, FileOperation op);

    /** Shell 命令白名单校验 */
    boolean isCommandAllowed(String commandToken);

    /** HTTP 域名白名单校验 */
    boolean isDomainAllowed(String url);
}

public enum FileOperation { READ, WRITE, LIST }
public record SandboxVerdict(boolean allowed, String reason) {}
```

**SandboxChecker 默认实现（核心阶段）**：

| 白名单类型 | 配置 key | 默认值 | 说明 |
|-----------|---------|--------|------|
| 文件路径 | `file.allowed_paths` | `[".oryxos/", "./workspace/"]` | 只允许在指定路径下读写 |
| Shell 命令 | `shell.allowed_commands` | `["ls","cat","echo","grep","find","wc","head","tail"]` | 只允许安全和只读命令 |
| HTTP 域名 | `http.allowed_domains` | `[]`（需手动配置） | 支持通配符如 `*.github.com` |

**NotifyTools 出站通知**：

Agent 完成任务后，通过 `notify` Tool 把结果推送到外部渠道。

```
Agent 对话完成
  → Agent 决定通知用户
  → 调用 notify(channel="dingtalk", message="告警处理完毕")
  → NotifyTools.execute():
      1. 查 Profile.notify_channels 获取 Webhook URL
      2. 构造渠道特定的消息格式:
         钉钉: {"msgtype":"text","text":{"content":"..."}}
         企业微信: {"msgtype":"text","text":{"content":"..."}}
         飞书: {"msgtype":"text","text":{"content":"..."}}
      3. HttpTools 发 POST 请求到 Webhook URL
      4. 返回 ToolResult(success=200/失败)
  → 通知送达（或失败记录）
```

**NotifyTools 支持的渠道（核心阶段）**：

| 渠道 | 适配器 | 实现 |
|------|--------|------|
| 钉钉 | `DingtalkNotifyAdapter` | 自定义机器人 Webhook |
| 企业微信 | `WecomNotifyAdapter` | 群机器人 Webhook |
| 飞书 | `FeishuNotifyAdapter` | 自定义机器人 Webhook |
| Webhook | `WebhookNotifyAdapter` | 通用 HTTP POST，用户自定义 URL 和格式 |

## 十三、已知技术风险与应对措施

| # | 风险 | 概率 | 影响 | 应对措施 |
|---|------|------|------|---------|
| 1 | **Spring AI Alibaba 版本不兼容** — GA 版本频繁变动 API，`ChatModel.call()` 方法签名可能不兼容 | 中 | 高 | (1) 锁定具体 GA 版本，不追 latest；(2) ProviderServiceImpl 中隔离所有 Spring AI 类型导入——只在这个类里 import Spring AI，其他地方不感知；(3) 如果 Spring AI Alibaba 稳定性不足，降级为 OkHttp 直接调 OpenAI 兼容 API（改动仅限于 ProviderServiceImpl 一个文件） |
| 2 | **SQLite 并发写入瓶颈** — 同步写入审计表在单用户 CLI 场景够用，但多用户 Web 场景下 WAL 模式也可能排队 | 低（核心阶段） | 中（扩展阶段） | (1) 核心阶段：单用户无并发，SQLite WAL 模式绰绰有余；(2) 扩展阶段：如果切换到 PostgreSQL，`SessionRepository` 等 JPA 接口一行不改，只换 dialect 和驱动；(3) 审计写入不放在主对话线程——用异步队列批量 flush 到 SQLite/数据库 |
| 3 | **LLM 返回格式变化** — Provider API 升级后 Function Calling 返回的 Tool Call 格式变化，解析失败 | 中 | 高 | (1) `FunctionCallingAdapter` 中加防御式解析：先按标准格式解析，失败则尝试常见变体格式；(2) 解析失败时记录原始返回内容到 `llm_calls` 的扩展字段；(3) 新增 Provider 前必须跑一遍 FC 回归测试（至少 3 个典型 Tool Call 场景） |
| 4 | **Virtual Thread 的 pinning 问题** — `synchronized` 块内调 IO 会导致 Virtual Thread pin 住载体线程，退化为 OS 线程 | 低 | 中 | (1) 所有涉及 IO 的代码块用 `ReentrantLock` 替代 `synchronized`；(2) 核心循环中 `ChatModel.call()` 和 `OryxTool.execute()` 不在 synchronized 块内执行；(3) 启动时加 `-Djdk.tracePinnedThreads=full` 监控 pinning |
| 5 | **内存溢出（MEMORY.md 无限增长）** — Agent 不断写 `save_memory`，文件超过预期大小 | 中 | 低 | (1) `LongTermMemory.truncateIfNeeded()` 每次写入后检查字数，超 4000 截头；(2) 扩展阶段加 TTL：每条记忆带过期时间，`recall_memory` 时过滤过期条目；(3) 管理台显示当前记忆容量并告警 |
| 6 | **Tool 执行超时拖死循环** — 一个慢 Tool（如 `shell` 跑一个长时间任务）占住 ReAct Loop，用户等到超时 | 中 | 中 | (1) 每个 Tool 执行设独立超时（`@Tool` 注解加 `timeout` 参数，默认 30s）；(2) ToolExecutor 用 `Future.get(timeout)` 模式，超时自动 cancel；(3) 超时后的 ToolResult 返回给 LLM："Tool 执行超时（30s），请尝试其他方法" |
| 7 | **Picocli + Spring Boot 启动冲突** — Picocli 的 `CommandLine.run()` 和 Spring Boot 的 `ApplicationRunner` 执行顺序不确定 | 低 | 低 | (1) 不在 Spring Boot 启动流程中跑 Picocli——`main()` 中先启动 Spring 容器，再 `ctx.getBean(CliCommand.class)` 后手动调 `CommandLine.run()`；(2) 如果 Picocli 的 `@Command` 注解类需要 Spring Bean，在 `CommandLine` 构造时传入 `IFactory` 从 Spring 容器获取 |

## 十四、待决议事项与触发条件

以下决策在核心阶段做了**临时选择**——在给定的 12 小时约束下单用户场景够用，但已知在多用户/生产环境下需要升级。每一项都有明确的触发条件和决议时间。

| # | 待决议事项 | 核心阶段临时选择 | 为什么临时 | 触发条件（满足任意一条即启动重新评估） | 重新决议的预期方向 | 决议人 |
|---|----------|----------------|----------|-------------------------------------|-----------------|--------|
| 1 | **数据库：SQLite → PostgreSQL** | SQLite + WAL 模式 | 零依赖，"java -jar 就跑"。单用户无并发 | (a) 同时 ≥3 个 Web 用户对话；(b) 单表行数 >100 万；(c) 需要主从复制或异地灾备 | 换 PostgreSQL。JPA Repository 接口不变，只换 dialect 和驱动。预计改动范围：1 个 pom.xml + 1 个 application.yml + schema.sql 轻微调整 | 架构负责人 |
| 2 | **Sandbox 白名单管理：静态配置 → 动态配置** | `application.yml` 硬编码白名单 | Web 管理台未就绪。核心阶段管理员可以直接改 yml | Web 管理台上线后（Feature 002） | 白名单配置从 yml 迁移到 Web 管理台，存储在 SQLite 的 `sandbox_rules` 表，支持 CRUD + 审计。SandboxChecker 接口不变，实现改为从数据库读规则 | 架构 + 安全负责人 |
| 3 | **Memory：文件系统 → 数据库 + 向量检索** | MEMORY.md 文件 + 子串匹配 | 单用户 MEMORY.md ≤ 4000 字，子串匹配够用 | (a) 单文件 >100 条记忆；(b) 检索延迟 >500ms；(c) 需要语义检索（"Spring Boot"匹配"Java 后端框架"） | 迁移到 SQLite FTS5 全文索引（仍零依赖），或 pgvector（如果 #1 已升级到 PG）。MEMORY.md 保留为人类可读的导出副本 | 架构负责人 |
| 4 | **Tool 执行审计：同步写入 → 异步批量** | 同步 INSERT，每次 Tool 执行后立即写 | 单用户场景写入延迟 <5ms，不影响体验 | 单个用户消息触发的 Tool 调用 ≥10 次（写入排队超过 50ms） | 引入内存队列 + 批量 flush（每 1 秒或每 50 条）。审计写入线程独立，不阻塞 ReAct Loop 主线程。不丢数据的保证：flush 前进程崩溃 → 从对话历史 JSON 恢复缺失的审计记录 | 架构 + 性能负责人 |
| 5 | **情景记忆（三层记忆的第三层）** | 不做。核心阶段只有会话记忆 + 长期记忆 | 12 小时窗口不够。情景记忆需要额外一张表 + Agent 决策链序列化逻辑 | 前两层记忆在生产环境跑 ≥1 个月，收集到真实使用数据后再设计 | 新增 `memory_entries` 表（见 §十二）。每个 ReAct 迭代的 Tool Call 决策链自动记录为一条情景记忆。过期时间默认 30 天 | 架构 + 产品负责人 |
| 6 | **oryxos-memory 模块独立** | MemoryTools 放在 `oryxos-tool` 模块，用文件系统实现 | 只有 2 个 Tool（save/recall），不值得单开模块 | 新增 ≥3 个 Memory 相关 Tool（如 search_memory、summarize_memory、forget_memory）或引入向量数据库依赖 | 从 `oryxos-tool` 拆出 `oryxos-memory` 模块，MemoryService 门面从 core 迁入 | 架构负责人 |
| 7 | **oryxos-sandbox 模块独立** | SandboxChecker 放在 `oryxos-tool` 模块 | 只有一个接口 + 一个实现，不值得单开模块 | 新增容器级隔离（Docker/gVisor）、或引入 eBPF/seccomp 等内核级沙箱、或需要独立的沙箱配置管理面 | 从 `oryxos-tool` 拆出 `oryxos-sandbox` 模块，SandboxChecker 接口从 core 迁入。tool 模块依赖 sandbox 模块 | 架构 + 安全负责人 |
| 8 | **Web 管理台前端** | 不做。核心阶段只有 CLI + REST API | 前端开发（Vue 3 + Vite）不在 12 小时窗口内 | 核心阶段 5 个 Demo 全部跑通 + REST API 稳定 ≥2 周 | 新建 `oryxos-admin-ui` 项目（独立 git repo），Vue 3 + Vite，产物部署到 `oryxos-web/src/main/resources/static/admin/` | 架构 + 前端负责人 |
