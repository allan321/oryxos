## 一、五个功能模块

### 模块 1：多 Provider 统一接入

**用户视角一句话**：管理员配置好模型，Agent 自动用上，切换模型不需要改 Agent 代码。

**核心功能点**：

- 管理员在配置文件中声明 Provider：名称、endpoint、API Key（从环境变量 `${VAR}` 读取，不写明文）
- 底座启动时加载所有 Provider，校验连通性，不可用时明确报错（哪个 Provider、什么原因）
- Agent Profile 中声明 `provider: deepseek` + `model: deepseek-chat`，底座自动路由到对应 Provider
- 同一个底座上，Agent A 用通义千问、Agent B 用 DeepSeek——独立配置，互不影响
- Provider 之间通过显式 `Map<String, ChatModel>` 映射，不靠 Spring 容器类型扫描
- 支持运行时增删 Provider（热加载，不重启底座）
- 每次 LLM 调用记录：哪个 Provider、哪个模型、token 用量（prompt/completion/total）、耗时（毫秒）

**输入规格**：
- `Profile` 对象（含 providerName, model, temperature, apiKey）→ 来自 AgentLoader
- `List<Message>` 对话历史 → 来自 ReActLoop
- `List<OryxTool>` 可用工具列表 → 来自 ToolRegistry

**输出规格**：
- `ChatResponse`（含 AssistantMessage：文本内容 或 ToolCall 列表）
- `LlmCallEntity`（审计记录：provider, model, promptTokens, completionTokens, totalTokens, durationMs）

**模块依赖**：
- 依赖 `oryxos-core`（ProviderService 接口、Profile 模型）
- 不依赖 tool / channel-cli / web

**配置项**：
- `application.yml` 中 `oryxos.providers` 列表：每个 Provider 的 name, endpoint, api-key-env-var
- 环境变量：`${PROVIDER_NAME}_API_KEY`

**错误模式**：
| 错误 | 检测方式 | 处理 |
|------|---------|------|
| API Key 无效 | HTTP 401 | 启动时报错：`Provider 'X': 认证失败 (401)` |
| Endpoint 不可达 | 连接超时 5s | 启动时报错：`Provider 'X': 无法连接 (Connection timeout)` |
| 模型不存在 | HTTP 404 | 调 LLM 时报错：`Model 'Y' not found on Provider 'X'` |
| 返回格式异常 | JSON 解析失败 | 记录原始返回内容到 llm_calls 扩展字段，向用户报错 |

**扩展点**：
- 新增 Provider：在 `application.yml` 中加一项配置 + 环境变量 → 不需要改代码
- Provider 热加载：`AgentLoader` 目录扫描触发时，`ProviderService` 重新读取配置并重建 ChatModel 实例
- 自定义 HTTP 头（如企业专线代理认证）：Provider 配置中增加 `headers` map

**验收标准**：

| # | 标准 | 量化 |
|---|------|------|
| 1 | 从配置文件到 LLM 调通 | 一个 `application.yml` + 环境变量 → `oryxos status` 显示 Provider 连通 |
| 2 | Provider 切换不影响 Agent | Agent A 从 DeepSeek 切到通义千问，只改一行配置，对话行为正常 |
| 3 | 坏 Provider 报错清晰 | 填错 API Key → `oryxos status` 输出 "deepseek: ✗ 连接失败 (401 Unauthorized)" |
| 4 | 审计记录完整 | 每次 LLM 调用在 `llm_calls` 表有一条记录，字段不缺 |

### 模块 2：ReAct 循环（Agent 运行时内核）

**用户视角一句话**：Agent 收到任务后自己想办法——查资料、调工具、看结果、再决定下一步，直到做完。

**核心功能点**：

- 用户消息进入 → PromptBuilder 组装完整 Prompt（System Prompt + 对话历史最近 N 轮 + 可用 Tool 列表）
- 调 LLM → 解析返回内容：无 Tool Call 则作为最终回复返回；有 Tool Call 则进入 Tool 执行链路
- Tool 执行链路：解析 Tool 名称和参数 → ToolRegistry 查找 → ToolExecutor 执行 → SandboxChecker 白名单校验 → 结果追加到对话历史 → 回到 LLM 继续推理
- 循环上限：默认 10 次迭代。达到上限时终止循环，返回已有信息并说明"任务未完成，已达到最大迭代次数"
- 错误处理三条规则：
  - Tool Call 参数与 Schema 不匹配 → 将格式错误传回 LLM，让它修正后重新生成（计一次迭代）
  - LLM 返回空内容 → 自动重试 1 次，告知 LLM "上次返回为空，请重新生成"；仍空则向用户报错
  - LLM 调用超时（默认 30 秒） → 直接向用户报错告知超时，不做自动重试
- 每次 LLM 调用写入 `llm_calls` 审计表，每次 Tool 执行写入 `tool_invocations` 审计表
- 循环全程同步阻塞，配合 Java 21 Virtual Thread 处理 IO 等待

**输入规格**：
- `String` 用户消息 → 来自 CliChannel 或 ApiController
- `Profile` 当前 Agent 配置 → 来自 AgentLoader（含 systemPrompt, maxIterations, maxHistoryTurns, toolNames）
- `Session` 当前会话（含对话历史） → 来自 SessionManager
- `List<OryxTool>` 可用工具 → 来自 ToolRegistry（按 Profile.toolNames 过滤）

**输出规格**：
- `String` 最终回复（Agent 对用户的文本响应）
- 副作用：`ToolInvocationEntity`（每次 Tool 执行一条）、`LlmCallEntity`（每次 LLM 调用一条）、Session.messages 更新

**模块依赖**：
- 依赖 `oryxos-core`（PromptBuilder、ToolExecutor、SessionManager 接口）
- 依赖 ProviderService（调 LLM）
- 依赖 ToolRegistry（查 Tool）
- 不依赖 channel-cli / web（引擎层不感知接入层）

**配置项（per Agent，来自 Profile）**：
- `maxIterations`（默认 10）
- `maxHistoryTurns`（默认 20）
- `llmTimeoutSeconds`（默认 30）

**错误模式**：
| 错误 | 检测方式 | 处理 |
|------|---------|------|
| 空返回（无 content 且无 toolCalls） | ChatResponse 解析 | 重试 1 次告知 LLM "上次返回为空"；仍空则向用户报错 |
| Tool Call 参数不匹配 Schema | JSON Schema 校验失败 | 构造错误 ToolResult 追加到对话 → LLM 下轮迭代修正 |
| LLM 超时 | Future.get(timeout) | 向用户报错告知超时，不自动重试 |
| 达到 maxIterations | iteration 计数器 | 终止循环，返回已有信息 + "达到最大迭代次数" |
| Tool 执行异常 | ToolResult.success=false | 追加到对话历史 → LLM 下轮迭代尝试其他方法 |
| Sandbox 拦截 | SandboxChecker.denied | 同上 |

**扩展点**：
- 自定义循环终止条件：`ReActLoop` 支持注入 `Predicate<LoopContext>` 终止判断（扩展阶段用于基于成本的提前终止）
- 中间审计 Hook：每次迭代完成后调 `AuditHook.onIteration(iteration, response, toolResults)`（扩展阶段用于实时合规检查）
- 流式输出适配：`ReActLoop` 返回类型从 `String` 扩展为 `Flux<String>`（扩展阶段，不改接口签名——新增重载方法）

**验收标准**：

| # | 标准 | 量化 |
|---|------|------|
| 1 | 无 Tool 调用的对话 | 从用户回车到 Agent 回复 ≤5 秒（正常网络） |
| 2 | 含 1 次 Tool 调用的对话 | 从用户回车到 Agent 最终回复 ≤10 秒 |
| 3 | 多轮上下文保持 | 第 5 轮对话，Agent 能正确引用第 1 轮的内容 |
| 4 | 循环超限终止 | max_iterations=2 + 需要 3 次 Tool 调用的任务 → 第 2 次迭代后终止，返回原因 |
| 5 | 错误不静默 | 任何 Tool/LLM 异常都有明确的错误信息返回给用户 |
| 6 | 审计覆盖率 | 100% 的 LLM 调用和 Tool 执行在审计表中有对应记录 |

### 模块 3：Agent 配置化（一个目录 = 一个 Agent）

**用户视角一句话**：创建一个文件夹、写一个 Markdown 文件，Agent 就存在了。不需要写 Java 代码。

**核心功能点**：

- `.oryxos/agents/<name>/AGENT.md` = Agent 的完整定义：YAML frontmatter（配置）+ 正文（任务指令）
- Frontmatter 字段：name, description, identity(agent_name, prompt), provider(name, model, temperature, api_key), tools[], mcp_servers[], channels[], bootstrap[], settings(max_iterations, max_history_turns)
- 可选子资源放同目录：`skills/*.md`（子指令，Agent 通过 `read_file` 按需读取）、`scripts/`（脚本，Agent 通过 `shell` 执行）、`REFERENCE.md`（参考资料）
- 底座启动时自动扫描 `agents/` 目录，每个子目录 = 一个 Agent，`AgentLoader.deriveProfile(dir)` 解析 frontmatter → `Profile` 对象
- API Key 从 frontmatter 的 `${VAR}` 格式读取环境变量，不写明文
- 支持 `--agent <name>` 参数指定用哪个 Agent；不指定则用 default
- 配置校验：启动时检查必填字段（name, provider.name, provider.model），缺失时给清晰报错

**输入规格**：
- 文件系统目录 `.oryxos/agents/<name>/`（含 AGENT.md + 可选 skills/、scripts/、REFERENCE.md）
- 环境变量（用于 `${VAR}` 占位符解析）

**输出规格**：
- `Map<String, Profile>`（key=agent name, value=完整 Profile 对象）
- 启动日志：每个 Agent 的加载状态（✓ 成功 / ✗ 失败 + 原因）

**模块依赖**：
- 依赖 SnakeYAML（解析 frontmatter）
- 不依赖 provider / tool / channel-cli / web
- AgentLoader 是引擎层的"数据入口"——其他模块通过 Profile 对象消费它的产出

**配置项（per Agent，来自 AGENT.md frontmatter）**：

| 字段 | 类型 | 必填 | 默认值 | 校验规则 |
|------|------|------|--------|---------|
| `name` | String | ✅ | — | 字母数字+连字符，≤64 字符 |
| `provider.name` | String | ✅ | — | 必须匹配 application.yml 中已注册的 Provider |
| `provider.model` | String | ✅ | — | 不做预校验（模型列表由 Provider 侧决定） |
| `provider.temperature` | Double | — | 0.7 | 0.0-2.0 |
| `provider.api_key` | String | ✅ | — | `${VAR}` 格式→从环境变量读取 |
| `tools[]` | List\<String\> | — | [] | 每个值必须匹配 ToolRegistry 中已注册的 Tool name |
| `settings.max_iterations` | int | — | 10 | 1-100 |
| `settings.max_history_turns` | int | — | 20 | 1-100 |

**错误模式**：
| 错误 | 检测方式 | 处理 |
|------|---------|------|
| AGENT.md 不存在 | 目录下无 AGENT.md | 跳过该目录，启动日志告警 |
| frontmatter 解析失败 | SnakeYAML 抛异常 | 启动时报错：`Agent 'X': YAML 格式错误 (第 Y 行)` |
| 必填字段缺失 | 字段为 null | 启动时报错：`Agent 'X': provider.name 为必填项` |
| `${VAR}` 环境变量不存在 | 正则匹配到 `${...}` 但 `System.getenv()` 返回 null | 启动时报错：`Agent 'X': 环境变量 DEEPSEEK_API_KEY 未设置` |
| tools[] 引用不存在的 Tool | ToolRegistry.get(name) 返回 null | 启动时告警：`Agent 'X': Tool 'Y' 未注册，已跳过`（不阻止启动） |

**扩展点**：
- 热加载：文件系统监听 `agents/` 目录变更 → 自动重新扫描 → 新 Agent 可用无需重启
- Profile 校验插件：`ProfileValidator` 接口，第三方可实现自定义校验规则（如企业命名规范）
- 远程 Profile 源：`ProfileSource` 接口，支持从 Git 仓库、配置中心加载 Agent 定义（扩展阶段）

**验收标准**：

| # | 标准 | 量化 |
|---|------|------|
| 1 | 零代码创建 Agent | 创建一个目录 + 写一个 AGENT.md → `oryxos status` 能看到这个 Agent |
| 2 | Profile 字段不漏 | frontmatter 的 12+ 字段全部正确映射到 Profile 对象 |
| 3 | 环境变量解析 | `api_key: ${DEEPSEEK_API_KEY}` → 从环境变量取值，启动时解析 |
| 4 | 错误提示清晰 | 缺少必填字段 → 报错 "Agent 'X': provider.name 为必填项" |
| 5 | 多 Agent 并存 | 3 个 Agent 目录 → `oryxos status` 列出 3 个，各自独立配置 |

### 模块 4：Tool 体系 + 沙箱执行

**用户视角一句话**：Agent 能干实际的事——读文件、执行命令、调 API。Tool 用任何语言写都行，挂上去就能用。

**核心功能点**：

- **OryxTool 统一接口**：getName(), getDescription(), getParametersJsonSchema(), execute(JsonNode) → ToolResult(success, content, errorMessage)
- **内置 Tool（9 个）**：read_file, write_file, list_dir, shell, http_get, http_post, save_memory, recall_memory, notify
- **Plugin Tool 三档接入**：
  - 零代码：写 SKILL.md + 复用社区 MCP Server
  - 轻代码：任何语言写 MCP Server，配置到 `mcp_servers.yaml`
  - 重代码：Java `@Tool` 注解 Spring Bean，进程内直接调用
- **ToolRegistry**：统一注册中心。内置 Tool + MCP Tool + Plugin Tool 一视同仁，都通过 name 查找
- **SandboxChecker 白名单**（核心阶段）：
  - 文件操作：路径白名单 `file.allowed_paths`
  - Shell 命令：命令首 token 白名单 `shell.allowed_commands`
  - HTTP 请求：域名通配符白名单 `http.allowed_domains`
  - 白名单之外的操作 → 拒绝执行并返回明确错误
- **Tool 选择原则**：能用零代码就不用轻代码，能用轻代码就不用重代码。降低 Tool 开发门槛
- **Tool 执行审计**：每次执行记录 tool_name, input_json, result_json, success, error_message, duration_ms

**输入规格**：
- `String toolName` + `JsonNode arguments` → 来自 ReActLoop（从 LLM 的 Tool Call 中解析）
- `SandboxVerdict` → 来自 SandboxChecker（白名单校验结果）

**输出规格**：
- `ToolResult`（success, content, errorMessage, toolCallId）→ 返回给 ReActLoop 追加到对话历史
- `ToolInvocationEntity`（审计记录：sessionId, toolName, inputJson, resultJson, success, errorMessage, durationMs）

**模块依赖**：
- 依赖 `oryxos-core`（OryxTool 接口、ToolRegistry 接口、SandboxChecker 接口）
- 依赖 SnakeYAML（解析 `mcp_servers.yaml`）
- 不依赖 provider / channel-cli / web

**Sandbox 白名单配置项**（`application.yml`）：

| 白名单类型 | 配置 key | 默认值 | 匹配规则 |
|-----------|---------|--------|---------|
| 文件路径 | `file.allowed_paths` | `[".oryxos/", "./workspace/"]` | `PathMatcher` 前缀匹配 |
| Shell 命令 | `shell.allowed_commands` | `["ls","cat","echo","grep","find","wc","head","tail"]` | 首 token 精确匹配 |
| HTTP 域名 | `http.allowed_domains` | `[]`（空=需手动配置） | 通配符匹配（`*.github.com`） |

**错误模式**：
| 错误 | 检测方式 | 处理 |
|------|---------|------|
| Tool 未注册 | ToolRegistry.get() 返回 null | 返回 ToolResult(success=false, error="Tool 'X' 未注册") |
| 参数不匹配 Schema | JSON Schema 校验 | 返回 ToolResult(success=false, error="参数格式错误: 缺少必填字段 'path'") |
| Sandbox 拦截 | SandboxChecker.check() 返回 DENIED | 返回 ToolResult(success=false, error="操作被沙箱拦截: 路径 '/etc/passwd' 不在白名单中") |
| Tool 执行超时 | Future.get(timeout) | 返回 ToolResult(success=false, error="Tool 执行超时 (30s)") |
| MCP Server 连接断开 | JSON-RPC 错误 | 返回 ToolResult(success=false, error="MCP Server 'X' 连接失败") |

**扩展点**：
- 新增内置 Tool：实现 `OryxTool` 接口 + 注册到 ToolRegistry → 不改核心代码
- MCP Server 动态注册：`mcp_servers.yaml` 热加载 → 新增 MCP Tool 实时可用
- SandboxChecker 策略升级：`SandboxChecker` 接口支持下实现类注入（扩展阶段：容器沙箱 `DockerSandboxChecker`、内核沙箱 `SeccompSandboxChecker`）
- Tool 市场（扩展阶段）：ToolRegistry 支持从远程注册中心拉取 Tool 元数据 + 签名校验

**验收标准**：

| # | 标准 | 量化 |
|---|------|------|
| 1 | 内置 Tool 可用 | `list_dir` 能列出当前目录文件，`read_file` 能读文件内容 |
| 2 | 零代码接入 | 配置一个 MCP Server → Agent 对话中能调它的 Tool |
| 3 | 沙箱拦截 | 尝试读白名单外的路径 → 拒绝执行，错误信息包含"不在白名单中" |
| 4 | Tool 异常回传 | Tool 执行失败 → 错误信息回传 LLM，Agent 向用户解释发生了什么 |
| 5 | 全审计 | `tool_invocations` 表中每条记录字段完整，success 字段准确 |

### 模块 5：Web Service + CLI 双通道

**用户视角一句话**：可以在终端直接跟 Agent 对话，也可以通过 HTTP API 让外部系统调 Agent。

**核心功能点**：

**Web API（10 个端点，前缀 `/api/v1`）**：

- `POST /sessions` — 创建会话，返回 session_id
- `POST /sessions/{id}/messages` — 发消息，触发完整 ReAct Loop，同步返回 Agent 回复
- `GET /sessions/{id}` — 查会话历史（所有消息 + 元数据）
- `DELETE /sessions/{id}` — 归档会话（软删除，status → archived）
- `POST /agents/{name}/invoke` — 无状态调用 Agent（不创建 Session）
- `GET /profiles` — 列出所有已加载的 Agent Profile
- `GET /memory` — 查询长期记忆（MEMORY.md 全文或关键词检索）
- `GET /tools` — 列出所有已注册的 Tool（内置 + MCP + Plugin）
- `GET /health` — 健康检查（返回 200 + 运行时长）
- `GET /info` — 运行信息 + 所有 Provider 连通状态

**CLI（12 个子命令）**：

- `oryxos init` — 初始化 `.oryxos/` 工作区
- `oryxos chat [--agent <name>]` — 交互式多轮对话（JLine readline，支持 `/exit`）
- `oryxos serve [--port 8080]` — 启动 HTTP API 服务
- `oryxos status` — 查看运行状态（Profile 列表 + Provider 连通性）
- `oryxos profile list/create/show/delete` — Profile 管理
- `oryxos provider list` — Provider 列表
- `oryxos tool list` — Tool 列表
- `oryxos session list` — 活跃 Session 列表

**关键约束**：
- 统一错误响应格式：`{ "code": "ERROR_CODE", "message": "人类可读描述" }`
- 空输入不发送给 LLM，重新显示提示符
- CLI 中输入 `/exit` 正常退出（保存 Session）
- API 不强制认证（核心阶段假设内网部署）

**输入规格**：
- **CLI 通道**：`String` 用户输入（来自 JLine readline）、命令行参数 `--agent <name>` / `--session <id>` / `--port <n>`
- **Web 通道**：HTTP 请求（JSON body）→ 来自外部系统或 Web 管理台

**输出规格**：
- **CLI 通道**：终端打印的 Agent 回复、`oryxos status` 状态信息、错误消息
- **Web 通道**：`ApiResponse<T>` JSON（code, message, data, timestamp）、HTTP 状态码

**模块依赖**：
- `oryxos-channel-cli`：依赖 core（调 ReActLoop、SessionManager、AgentLoader）
- `oryxos-web`：依赖 core（同上）
- channel-cli 和 web 之间零依赖（平级）

**配置项**：

| 配置项 | 来源 | 默认值 | 说明 |
|--------|------|--------|------|
| `server.port` | application.yml / `--port` | 8080 | Web API 监听端口 |
| `cli.prompt` | application.yml | `"OryxOS> "` | CLI 提示符 |
| `cli.history_file` | application.yml | `.oryxos/cli_history` | JLine 命令历史文件路径 |

**错误模式**：
| 错误 | HTTP 状态 | CLI 行为 |
|------|----------|---------|
| Profile 不存在（`--agent nonexist`） | 404 | 打印 "Agent 'nonexist' 不存在。可用 Agent: [...]" 并退出 |
| Session 不存在（`--session xxx`） | 404 | 打印 "Session 'xxx' 不存在或已归档" 并退出 |
| 请求体 JSON 格式错误 | 400 | — |
| LLM 超时 | 504 | 打印 "LLM 调用超时 (30s)，请重试" |
| 内部异常 | 500 | 打印错误信息 + 堆栈（DEBUG 模式） |

**扩展点**：
- 新增渠道：实现 `Channel` 接口（`onMessage(String) → String`）→ 不改 core。扩展阶段加企微/钉钉/飞书渠道
- API 版本演进：`/api/v1` → `/api/v2`，旧版本保留至少 3 个月
- SSE 流式端点（扩展阶段）：新增 `GET /sessions/{id}/messages/stream`，不修改现有同步端点
- Web 管理台前端（扩展阶段）：独立 Vue 3 项目，调 REST API，部署到 `oryxos-web` static 资源目录

**验收标准**：

| # | 标准 | 量化 |
|---|------|------|
| 1 | 10 个端点全部可达 | `curl` 每个端点，返回正确 JSON + 200/201 |
| 2 | CLI 交互式对话 | `oryxos chat` → 输入 → 回复 → `/exit` 正常退出 |
| 3 | 错误响应格式统一 | 任何异常 → 返回 `{"code":"...","message":"..."}` |
| 4 | 健康检查 | `GET /health` → `{"status":"UP","uptime":"..."}` |

## 二、不做清单：刻意不做的 10 件事

> **收窄是需求文档最难但最重要的部分。** 以下每一项都是经过深思熟虑的"不做"决策。每一项都标注了"为什么不做"和"什么时候做"。

| # | 不做的事 | 为什么不做 | 什么时候做 |
|---|---------|----------|----------|
| 1 | **多租户 RBAC** | 核心阶段只有单用户 CLI。权限模型需要先有真实使用数据才能设计——现在拍脑袋定义角色 = 返工 | 扩展阶段 |
| 2 | **SSO / LDAP / OAuth 集成** | 核心阶段假设内网部署，不引入外部认证依赖。接了就要维护 token 刷新、会话过期、PKI 证书——ROI 极低 | 扩展阶段 |
| 3 | **SSE / 流式响应** | 流式是异步范式，跟核心阶段"同步阻塞 + Virtual Thread"冲突。先稳定同步链路，再开异步分支 | 扩展阶段 |
| 4 | **WebSocket 长连接** | 同上。而且 WebSocket 需要独立管理面：心跳、重连、背压、会话亲和性——全是工程债 | 扩展阶段 |
| 5 | **限流 / 熔断 / 降级** | 单用户 CLI 不存在并发问题。这些是分布式多租户的需求，不是内核需求 | 扩展阶段 |
| 6 | **可视化的 Workflow 编排界面** | OryxOS 是底座，不是编排平台。编排是 Dify/Coze 的事。底座做编排 = 跨界竞争 = 分散精力 | 不做。跟 Dify 互补 |
| 7 | **跨 Agent 协作（A2A 协议）** | 单个 Agent 都还没跑稳，就去搞 Agent 间对话——空中楼阁。先让一个 Agent 零 bug 跑完 ReAct Loop | 扩展阶段 |
| 8 | **Agent 自进化 / 自动 Skill 蒸馏** | 不是底座的职责。底座管 Agent 的"运行生命周期"，不管"智能进化"。后者是 Hermes Agent 的定位 | 不做。跟 Hermes 互补 |
| 9 | **Skill 市场 / 社区生态** | OpenClaw 的 341 个恶意 Skill 是前车之鉴。供应链安全机制没建立之前开放市场 = 引狼入室 | 扩展阶段（需先有 Skill 签名校验） |
| 10 | **多语言 SDK（Python / Node.js / Go）** | 核心阶段聚焦 Java 原生体验。SDK 是 API 之后的活——先有稳定的 REST API，再给其他语言写 wrapper | 扩展阶段 |

### 不做清单的核心逻辑

这 10 项可以归为三类，每一类背后的原则比清单本身更重要：

**第一类：没到时机（#1-5）**。这些是"对的决策，错的时间"。多租户、SSO、流式、限流——每一项在扩展阶段都是必须做的。但在核心阶段做就是**过度设计**：在没用户、没并发、没生产数据的时候就为"未来可能的需求"搭架构。

**第二类：不是我们的事（#6-8）**。编排是 Dify 的事，自进化是 Hermes 的事。OryxOS 的核心价值是"让一群 Agent 可靠运行"——不是"让一个 Agent 超强"，不是"让 workflow 可视化"。**知道自己不是什么都做，比知道要做什么更难。**

**第三类：没到安全水位（#9）**。OpenClaw 的教训：在没有 Skill 签名校验、来源验证、沙箱隔离的情况下开放生态 = 给攻击者开门。安全水位不够的时候，"少做"是"做对"的前提。

## 四、两个端到端验收 Demo

> 每个 Demo 必须串起**至少 3 个核心能力**。不是单元测试，是"用户能看到的真东西"。

### Demo 一：查天气穿衣

**串起能力**：Provider（#1）+ ReAct（#2）+ Tool（#4）+ CLI（#5）= 4 个

**场景**：用户问"今天北京天气怎么样，该穿什么衣服"。Agent 必须**主动**调 `http_get` Tool 获取真实天气数据（不能编造），基于数据给出穿衣建议。

**完整链路**：
```
CLI 输入: "今天北京天气怎么样"
  → ReActLoop (iteration 1):
      PromptBuilder 组装: System Prompt + 历史 + Tool 列表(含 http_get)
      → ProviderService.call(DeepSeek)
      → LLM 回复: { toolCalls: [{ name:"http_get", args:{url:"https://api.weather.com/beijing"} }] }
      → 写入 llm_calls 审计 (一条)
      → ToolExecutor.execute("http_get", {url:"..."})
          → SandboxChecker 校验域名白名单 ✓
          → 执行 http_get → 返回: { "temp":5, "weather":"晴", "wind":"3级" }
          → 写入 tool_invocations 审计 (一条)
      → 追加工具结果到对话历史
  → ReActLoop (iteration 2):
      ProviderService.call(包含天气数据)
      → LLM 回复: { content: "北京今天晴，气温5°C，风力3级。建议穿..." }
      → 写入 llm_calls 审计 (又一条)
  → 返回最终回复给 CLI
```

**验收检查 6 条**：
- [ ] Agent 回复中包含北京天气的真实数据（温度 + 天气状况——不是 AI 编的）
- [ ] Agent 回复中包含穿衣建议
- [ ] `tool_invocations` 表有 1 条 `http_get` 记录，success=true
- [ ] `llm_calls` 表有 2 条记录（初始推理 + 最终回复）
- [ ] 端到端耗时 ≤10 秒
- [ ] 把 `http_get` 域名改成不在白名单的 → Agent 报错"操作被沙箱拦截"

### Demo 二：跨对话记忆

**串起能力**：ReAct（#2）+ Agent 配置化（#3）+ Tool（#4）+ CLI（#5）= 4 个

**场景**：用户在第一段对话中告诉 Agent 自己的偏好，Agent 通过 `save_memory` 写入 MEMORY.md。退出后启动第二段对话（新 Session），Agent 通过 `recall_memory` 记起偏好并体现在回复中。

**完整链路**：
```
对话一 (Session A):
  CLI 输入: "我叫张三，最喜欢用 Spring Boot 做后端"
  → ReActLoop: LLM 推理 → 决定调 save_memory
  → save_memory("用户叫张三，最喜欢用 Spring Boot 做后端")
  → MEMORY.md 追加: "- 用户叫张三，最喜欢用 Spring Boot 做后端"
  → 写入 tool_invocations (一条)
  → Agent 回复: "好的张三，我记住了"
  → /exit → Session A 持久化到 SQLite

对话二 (Session B - 新 Session):
  CLI 输入: "我应该用什么框架？"
  → PromptBuilder: System Prompt + (空对话历史: 新 Session) + MEMORY.md 内容
  → LLM 看到 memory 中有"张三偏好 Spring Boot"
  → 无需调 Tool，直接回复: "张三，根据你的偏好，我建议用 Spring Boot..."
  → 写入 llm_calls 审计 (一条)
```

**验收检查 6 条**：
- [ ] 对话一结束后，MEMORY.md 文件中包含"张三"和"Spring Boot"
- [ ] 对话二中 Agent 回复中提到"张三"（不是用户先说的——Agent 自己回忆的）
- [ ] 对话二中新 Session 对话历史初始为空（验证记忆不是从历史来的）
- [ ] `tool_invocations` 表有 1 条 `save_memory` 记录（对话一）
- [ ] 对话二恢复后，输入"我上次说了什么偏好"→ Agent 能引用对话一的偏好
- [ ] 手动在 MEMORY.md 中写超过 4000 字 → 注入到 System Prompt 时被截断，不超上下文窗口

## 五、三个典型场景

### 场景 A：运维助手

> 某电商公司运维团队有 5 个人，日常要处理服务器告警、查日志、重启服务、更新配置。告警每天几十条，每条都要人去看、判断、操作。动作不复杂但重复度高，占用了大量人力。

**怎么用 OryxOS**：

运维负责人创建一个 `ops-agent`：写一个 `AGENT.md` 定义人设（"你是一个运维助手，负责处理服务器告警"），配置使用 DeepSeek + `shell`/`http_get`/`http_post`/`read_file` Tool，渠道对接钉钉群。

告警系统发 Webhook → OryxOS Web API → ops-agent 收到告警 → 自动查日志（`shell` 调 `tail`/`grep`）→ 判断严重程度 → 如果是已知问题，自动执行修复脚本（`shell`）→ 把处理结果发到钉钉群（`notify`）。如果是未知问题，直接在钉钉群里 @运维人员并附上初步诊断。

**关键价值**：80% 的告警是已知套路。Agent 自动处理掉，运维人员只介入那 20%。

---

### 场景 B：知识管理助手

> 某律所有 200 名律师，内部有数万份判例文档、合同模板、法规库。律师每次接新案子，先要在知识库里翻半天。资深律师的经验在脑子里，无法被新人复用。

**怎么用 OryxOS**：

IT 团队写一个检索 Tool（Python MCP Server，对接内部 Elasticsearch 判例库），注册到 OryxOS。创建一个 `legal-assistant` Agent，配置 `read_file` + 自定义检索 Tool + `save_memory`/`recall_memory`。

律师在 Web 端问："找一下 2024-2025 年上海知识产权法院关于商标侵权的判例，金额超过 100 万的"。Agent 调检索 Tool 获取列表 → 用 `read_file` 读几个重点判例全文 → 生成摘要报告。律师追问："类似的案子我们所去年接过吗"→ Agent 调 `recall_memory` 查历史记忆 → 找到相关记录回复。

**关键价值**：知识从"人脑里的隐性经验"变成"Agent 可检索的数字资产"。新人上手速度提升。

---

### 场景 C：销售助手

> 某 B2B 制造企业有 50 名销售，每人每天要准备报价、查库存、回答客户技术问题、跟进合同。信息散落在 ERP、CRM、产品手册三个系统里，销售平均每天花 2 小时在系统间切换查信息。

**怎么用 OryxOS**：

Tool 开发者写三个 MCP Server：ERP 查询（查库存+价格）、CRM 查询（查客户历史）、产品手册检索（RAG 搜索 PDF）。OryxOS 上创建一个 `sales-assistant` Agent，配置这三个 MCP Server + `http_post`（发邮件/企微）。

销售在企业微信上问："给客户 A 报一个 100 台型号 X 的报价"。Agent 调 ERP 查型号 X 的当前价格和库存 → 调 CRM 查客户 A 的历史订单和信用额度 → 生成报价草稿（含价格、交期、建议条款）→ 发到销售的企业微信。

**关键价值**：2 小时的信息检索变成 2 分钟的 Agent 对话。销售把时间花在"跟客户谈"上，不是"在系统间查"上。

## 六、五条关键流程

### 流程 1：工作区初始化（`oryxos init`）

```
用户执行: oryxos init
  → 检查当前目录是否已有 .oryxos/
  → 已有则提示 ".oryxos/ 已存在，跳过初始化"
  → 没有则创建目录树:
      .oryxos/
      ├── agents/          (空目录，放 Agent 定义)
      ├── memory/
      │   └── MEMORY.md    (空文件，Agent 通过 save_memory 写入)
      ├── sessions/        (备用目录，Session 已迁入 SQLite)
      ├── logs/            (结构化日志输出)
      ├── mcp_servers.yaml (MCP Server 配置模板)
      ├── oryxos.db        (SQLite 数据库文件)
      ├── AGENTS.md        (Bootstrap: 项目级 Agent 行为说明 - 空模板)
      ├── SOUL.md          (Bootstrap: Agent 人格定义 - 空模板)
      └── USER.md          (Bootstrap: 用户偏好 - 空模板，只读)
  → 输出: "✓ .oryxos/ 工作区已初始化"
```

### 流程 2：Profile 创建（创建 AGENT.md）

```
用户操作: 创建 .oryxos/agents/default/AGENT.md
  → 写入 YAML frontmatter + 正文
  → 底座启动时 AgentLoader 扫描 agents/ 目录
  → 对每个子目录:
      读 AGENT.md → 用 SnakeYAML 解析 frontmatter
      → 校验必填字段(name, provider.name, provider.model)
      → 解析 ${VAR} 环境变量
      → 派生 Profile 对象
      → 正文作为 systemPrompt 字段
  → 所有 Profile 注册到内存，可通过 API/CLI 查询
  → 如果校验失败，启动时报错: "Agent 'X': [字段名] 为必填项"
```

### 流程 3：消息处理（ReAct Loop 完整链路）

```
用户消息 "读一下 test.txt 的内容"
  → CliChannel 收到消息，传给 ReActLoop
  → ReActLoop 迭代开始 (iteration=1):
      ├─ PromptBuilder.assemble():
      │    [1] System Prompt (AGENT.md 正文)
      │    [2] 对话历史 (最近 max_history_turns 轮)
      │    [3] 可用工具列表 (ToolRegistry.toFunctionCallingFormat())
      │    [4] 用户消息
      ├─ ProviderService.call(messages, tools):
      │    LLM 返回: { toolCalls: [{ name: "read_file", args: {path: "test.txt"} }] }
      │    写入 llm_calls 审计表
      ├─ ReActLoop 发现 toolCalls 不为空:
      │    ├─ ToolExecutor.execute("read_file", {path: "test.txt"})
      │    │    ├─ ToolRegistry.get("read_file") → FileTools.readFile
      │    │    ├─ SandboxChecker.check("file", "test.txt") → 白名单通过
      │    │    ├─ Files.readString(Path.of("test.txt")) → "Hello from OryxOS!"
      │    │    └─ 返回 ToolResult(success=true, content="Hello from OryxOS!")
      │    ├─ 写入 tool_invocations 审计表
      │    └─ ToolResult 转为 ToolMessage 追加到对话历史
      └─ 进入下一次迭代 (iteration=2)
  → ReActLoop 迭代继续 (iteration=2):
      ├─ ProviderService.call(更新后的 messages, tools)
      │    LLM 返回: { content: "test.txt 的内容是：\"Hello from OryxOS!\"" }
      │    写入 llm_calls 审计表
      └─ ReActLoop 发现无 toolCalls → 这是最终回复
  → 返回 "test.txt 的内容是：\"Hello from OryxOS!\""
  → Session 追加此轮消息
```

### 流程 4：Tool 调用（完整生命周期）

```
LLM 返回 Tool Call
  → ToolExecutor.execute(toolName, arguments):
      1. ToolRegistry.get(toolName)
         → 找到了 → 获取 OryxTool 实例
         → 没找到 → 返回 ToolResult(success=false, errorMessage="Tool 'X' 未注册")
      2. 参数校验
         → arguments 与 OryxTool.getParametersJsonSchema() 比对
         → 格式匹配 → 继续
         → 格式不匹配 → 返回 ToolResult(success=false, errorMessage="参数格式错误: ...")
                        → ReActLoop 将此错误作为 ToolMessage 追加到对话
                        → LLM 在下一轮迭代中修正参数
      3. SandboxChecker.check(toolName, arguments)
         → 文件操作: 路径在白名单内 → 放行
         → Shell 命令: 命令首 token 在白名单内 → 放行
         → HTTP 请求: 域名匹配白名单 → 放行
         → 不在白名单内 → 返回 ToolResult(success=false, errorMessage="操作被沙箱拦截")
      4. 执行: OryxTool.execute(arguments) → ToolResult
      5. 审计: 写入 tool_invocations 表 (session_id, tool_name, input, result, success, duration_ms)
      6. 返回 ToolResult
```

### 流程 5：Session 管理（创建 → 持久化 → 恢复）

```
Session 创建:
  用户启动 oryxos chat --agent default
  → SessionManager.create("default", "cli", "cli-user")
  → 生成 session_id = "cli-cli-user-default-{timestamp}"
  → INSERT INTO sessions (session_id, profile_name, channel, user_id, status)
  → messages_json = [] (初始空)

对话进行中:
  每轮对话后:
  → Session.messages.append(userMessage)
  → Session.messages.append(assistantMessage)
  → messages_json = JSON.serialize(messages)
  → UPDATE sessions SET messages_json = ?, last_active_at = NOW()

Session 退出:
  用户输入 /exit
  → CliChannel.shutdown()
  → SessionManager.save(sessionId, messages)  (同上，最后一次持久化)
  → 输出 "再见!" → 退出进程

Session 恢复:
  用户执行 oryxos chat --session cli-cli-user-default-xxx
  → SessionManager.load("cli-cli-user-default-xxx")
  → SELECT * FROM sessions WHERE session_id = ? AND status = 'active'
  → List<Message> messages = JSON.deserialize(messages_json)
  → 如果消息数 > max_history_turns * 2:
      截断到最近 max_history_turns 轮
  → 注入到 ReActLoop 的对话历史
  → 用户继续对话，Agent 引用历史内容

Session 归档:
  DELETE /api/v1/sessions/{id}
  → UPDATE sessions SET status = 'archived', archived_at = NOW()
  → 软删除，数据保留
```

| `agentName` | String | — | name | 展示名，如"运维小欧" |

| `providerName` | String | ✅ | — | Provider 映射 key，如 `"deepseek"` |
| `model` | String | ✅ | — | 模型名，如 `"deepseek-chat"` |

### 4.2 Session（SQLite 表：`sessions`）

| 字段 | SQL 类型 | 约束 | 说明 |
|------|---------|------|------|
| `session_id` | VARCHAR(255) | PK | `{channel}-{userId}-{profileName}-{timestamp}` 格式，保证唯一 |
| `profile_name` | VARCHAR(255) | NOT NULL | 外键关联 Profile.name |
| `channel` | VARCHAR(50) | NOT NULL | 渠道标识：`cli`, `web`, `wecom`, `dingtalk` 等 |
| `user_id` | VARCHAR(255) | NOT NULL | 用户标识。CLI 场景默认 `"cli-user"` |
| `messages_json` | TEXT | NOT NULL | `List<Message>` 的 JSON 序列化 |
| `status` | VARCHAR(20) | NOT NULL, DEFAULT 'active' | `active` / `archived` |
| `created_at` | TIMESTAMP | DEFAULT CURRENT_TIMESTAMP | |
| `last_active_at` | TIMESTAMP | DEFAULT CURRENT_TIMESTAMP | 每次对话后更新 |
| `archived_at` | TIMESTAMP | NULLABLE | 归档时间 |

### 4.3 Message（JSON 数组元素，内嵌于 sessions.messages_json）

| 字段 | JSON 类型 | 说明 |
|------|----------|------|
| `role` | String | `"user"` / `"assistant"` / `"tool"` |
| `content` | String | 消息文本。tool 角色时为 Tool 执行结果 |
| `toolCalls` | Array\<ToolCallData\> \| null | **仅 assistant**。LLM 返回的 Tool Call 列表 |
| `toolCallId` | String \| null | **仅 tool**。关联的 Tool Call ID |
| `timestamp` | Long | epoch millis |

**ToolCallData（内嵌在 Message.toolCalls[]）**：

| 字段 | JSON 类型 | 说明 |
|------|----------|------|
| `id` | String | LLM 生成的 Tool Call ID，用于关联 tool 角色的消息 |
| `name` | String | Tool 名称，如 `"read_file"` |
| `arguments` | String | JSON 参数字符串，如 `"{\"path\":\"test.txt\"}"` |

### 4.4 Memory（文件系统：`MEMORY.md`）

| 属性 | 说明 |
|------|------|
| **存储位置** | `.oryxos/memory/MEMORY.md` |
| **写入方式** | Agent 通过 `save_memory` Tool 追加文本 |
| **读取方式** | Agent 通过 `recall_memory` Tool 关键词检索；系统注入 System Prompt 时最多取 4000 字 |
| **格式** | Markdown 文件，人工可读 |
| **管理规则** | 用户只读不写（Agent 的"成长日记"）；超 4000 字自动截断保留最近内容 |
| **与 USER.md 的区别** | USER.md：用户手写的初始设定，OryxOS 只读不写。MEMORY.md：Agent 的运行时记忆，OryxOS 读写 |
